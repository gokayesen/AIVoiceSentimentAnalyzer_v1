- (constraint) Hard product-principle constraints on the architecture (from Product Brief/PRD, non-negotiable): (1) voice-first — acoustic signal is a first-class analytical input, architecture must never let the pipeline silently degrade to transcript-only analysis; (2) human-in-the-loop — system produces evidence for analyst review, never an autonomous final decision; (3) explainability/uncertainty — every analytical output must be confidence-qualified and evidence-linked; (4) technical-depth — portfolio principle, architecture should demonstrate real engineering depth (per Product Brief Guiding Principles)
- (decision) Audio input handling: support both mono and stereo, detect channel count at ingest. Stereo -> deterministic per-channel speaker split (no diarization needed). Mono -> run a diarization model. Chosen over stereo-only/mono-only because EXPERIENCE.md already defines three distinct speaker-attribution states (unavailable/uncertain/confident) and only this path can genuinely exercise all three in MVP demo data. Resolves Technical Research §5's top architecture-blocking question.
- (constraint) SER (acoustic emotion) inference must run locally/open-weight — [ADOPTED as fact, not elicited]. Technical Research §10.1 verified no major cloud provider (Azure/AWS/Google) offers a genuine acoustic voice-emotion API; cloud 'sentiment' offerings operate on transcript text only. No cloud path exists for acoustic SER specifically.
- (decision) STT (speech-to-text) inference: local, open-weight (e.g. faster-whisper/whisper.cpp family), not a cloud API. Chosen for consistency with the project's privacy/data-retention posture (PRD §10 minimal retention, no third-party audio egress), cost-at-low-volume, and the portfolio technical-depth principle. User confirmed over the cloud-STT alternative (OpenAI Whisper API / Azure / Google STT).
- (decision) Model serving/runtime boundary: single consolidated Python ML/audio service hosts STT + SER + fusion in one process/deployment boundary, with clean internal module separation (not network-separated microservices). Chosen for single-developer/portfolio-scale project with no production infra budget (PRD §10 Cost/Processing) -- avoids unneeded distributed-systems complexity. This service is architecturally distinct from the web frontend/API layer (paradigm-level boundary, not a further ML-internal split).
- (decision) SER primary classifier: fine-tuned embedding model (Wav2Vec2/HuBERT/WavLM family) on CREMA-D + IEMOCAP (eval-only for IEMOCAP per its license), per Technical Research §1.2/§3.4 recommendation. Handcrafted acoustic features (pitch/F0, energy, speaking rate, pauses/voice-activity) are computed as a separate, mandatory explainability/evidence layer feeding DESIGN.md's acoustic-metric-bar -- not the primary classifier input, required regardless of classifier choice since DESIGN.md already mandates named-feature evidence.
- (decision) Emotion taxonomy: small coarse category set (4-6 classes, CREMA-D-style: Angry/Happy/Sad/Neutral +1-2), each mapped via a fixed lookup table to one of DESIGN.md's 4 polarity colors (negative/mixed/positive/neutral) for the badge-dot/timeline-glyph visual system. Chosen over collapsing Emotion directly onto the 4-value polarity scale: preserves EXPERIENCE.md's richer example labels (Frustration, Calm, Resignation) while keeping model classes coarse enough to match Technical Research §1.5's cross-domain accuracy finding (4-class UA drops 63%->45.6% domain-gap vs. only 81.1%->76.9% for 2-class).
- (decision) STT engine: faster-whisper (CTranslate2-based), local, Python-native, word-level timestamps for evidence-linkage (FR-13/NFR-1). Runs in the same consolidated ML/audio service as SER.
- (decision) Diarization (mono path only): WhisperX orchestrates faster-whisper transcription + forced alignment + pyannote.audio diarization together for mono input. Stereo path does NOT use WhisperX or diarization -- faster-whisper runs independently per channel, speaker identity comes from channel index, not a model. Must pin to pyannote.audio's MIT-licensed 3.1 pipeline specifically (Technical Research §5.2-5.3 flags community-1 as CC-BY-4.0 and precision-2 as commercial-only -- architecture must not depend on either).
- (decision) Fusion mechanism: rule-based late fusion. Confidence-weighted averaging of calibrated acoustic-emotion and text-sentiment signals produces the fused Sentiment/Emotion + Confidence. An explicit disagreement rule (polarity mismatch between the two modalities, both above a configurable confidence floor) triggers FR-11's dual-signal-panel display instead of collapsing to one number. Chosen per Technical Research §6.2-6.3 (no jointly-labeled multimodal call-center dataset exists to train a fusion model; rule-based is auditable and matches the explainability/human-in-the-loop principles). Exact disagreement threshold value is a tunable config parameter, not fixed in the spine (mirrors PRD's own deferral of threshold values to evaluation work).
- (decision) Confidence/uncertainty generation: temperature scaling calibrates each modality's native softmax confidence (required MVP baseline per Technical Research §6.4); MC Dropout (K stochastic forward passes at inference, dropout active) adds a second uncertainty signal via prediction variance. Feasible because processing is batch/async with no sub-second latency NFR (PRD §10). Both calibrated-confidence and MC-Dropout-variance feed into the fusion rule's weighting and the low-confidence flagging threshold.
- (constraint) Two confidence/uncertainty axes must be tracked and surfaced independently, never conflated into one score: (1) Sentiment/Emotion confidence (from calibrated fusion + MC Dropout), and (2) speaker-attribution/diarization confidence (from WhisperX/pyannote, mono path only). This is a hard data-model requirement, not a UI-only concern -- EXPERIENCE.md's State Patterns explicitly requires these to co-occur and be legible independently on the same transcript turn (e.g. a confident Sentiment reading with uncertain speaker attribution).
- (decision) Chunking/timeline unification: VAD-detected natural speech boundaries serve as BOTH the model-input chunk boundaries (technical necessity -- STT/SER max input length) AND the Emotional Timeline segment boundaries (FR-9 product requirement) -- one mechanism, not two. Rolling context carried across chunk boundaries per Technical Research §11 to protect timeline/sentiment integrity from chunk-boundary artifacts.
- (decision) Storage: SQLite (structured Analysis Results, Call metadata, status) + a session-scoped local filesystem directory (uploaded audio, intermediate artifacts). Chosen over pure in-memory/ephemeral storage for dev/demo resilience (survives process restart) while remaining fully session-scoped and user-deletable -- satisfies PRD §10's 'no persistent-storage guarantee' as a product promise (deletable, not silently accumulated), not a literal in-memory-only implementation mandate. No data leaves this local boundary to any third party.
- (decision) Async processing orchestration: RQ + Redis lightweight task queue. Web/API layer enqueues a Call-processing job on upload; the consolidated ML/audio service's worker(s) consume it independently of the web process -- gives FR-3's queued/processing/complete/failed status tracking, non-blocking behavior across Calls, and retry-on-failure for free from the queue's own semantics, and survives web-process restarts (status isn't lost). One additional lightweight infra dependency (Redis, single container) -- acceptable for portfolio scope, chosen over in-process BackgroundTasks/asyncio for resilience and to demonstrate real background-worker engineering.
- (decision) Evaluation strategy: adopted as-is from Technical Research §8.4 -- majority-class baseline, then single-modality baselines before crediting fusion with any benefit, public-benchmark numbers (IEMOCAP/CREMA-D) labeled explicitly as optimistic upper-bounds pending in-domain validation, small manually-annotated in-domain validation set as the honest baseline. UAR/macro-F1 as headline metrics (§8.1) given class imbalance. Directly supports NFR-2/NFR-5 (no unproven calibration/accuracy claims).
