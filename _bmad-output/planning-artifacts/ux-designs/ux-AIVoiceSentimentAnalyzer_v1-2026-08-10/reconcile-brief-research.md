# Reconciliation: Product Brief + Technical Research vs. UX Spine

Scope: `DESIGN.md` and `EXPERIENCE.md` checked against `brief.md`, `addendum.md`, and `technical-voice-sentiment-analyzer-research-2026-08-10.md`. PRD reconciliation is out of scope (checked separately). No spine files were edited.

## Gaps found

### 1. Acoustic-insights panel never names an actual acoustic feature — risks reading as decorative despite good structural bones

- **Description:** The only spec for the acoustic evidence panel is the generic `Acoustic metric bar` component ("label + measured value over a horizontal bar... paired with a short note tying the acoustic panel back to the specific transcript moment it supports"). Neither `DESIGN.md` nor `EXPERIENCE.md` names a single concrete acoustic feature anywhere (confirmed by search: zero occurrences of "pitch," "F0," "energy," "speaking rate," "pause," "jitter," "shimmer," or "MFCC" in either file). Technical Research §3.3/§3.4 is specific about which features carry the product's explainability value (F0 statistics, energy/RMS, speaking rate, VAD-derived pauses, MFCCs) and gives a concrete example of what "inspectable as real evidence" should look like: *"a QA analyst asking 'why was this flagged?' can be shown 'pitch rose 40Hz, rate +20%, energy spiked.'"* The current spec's traceability mechanism (moment-anchored note) is sound and correctly required, but with no named metrics anywhere in the visual/behavioral spec, the panel is one implementation choice away from being generic "some measured value" bars rather than the labeled, feature-specific evidence Guiding Principle #4 (technical depth, not token inclusion) and Principle #1 (voice-first, acoustic as evidence not decoration) call for. Relatedly, the Dashboard's main-content split gives the transcript ~60% width vs. acoustic ~40% (`DESIGN.md` Layout & Spacing) — plausibly just prose-readability ergonomics, but combined with the unnamed-metric issue it tilts the panel further toward feeling secondary rather than co-equal primary evidence.
- **Location:** `DESIGN.md` → Components → "Acoustic metric bar"; `EXPERIENCE.md` → Component Patterns → "Acoustic metric bar"; `DESIGN.md` → Layout & Spacing (60/40 split).
- **Suggested fix:** Name representative acoustic metrics as part of the component spec (e.g., "Pitch (F0)," "Energy," "Speaking Rate," "Pause Ratio" — pulling directly from Technical Research §3.3's MVP feature list) so the panel is unambiguously tied to specific extracted signals, not a generic bar. Optionally, add the "pitch rose 40Hz, rate +20%" style phrasing as an example note format in Voice and Tone to lock in the concrete-evidence register.

### 2. No distinction between "low signal confidence" and "low speaker-attribution confidence" — diarization's hardest failure mode isn't reflected

- **Description:** Technical Research §5.4 makes a specific, flagged point: overlapping/emotionally-charged speech is both (a) more likely to occur at exactly the moments this product cares about most, and (b) the condition under which diarization confidence is systematically lower — meaning speaker attribution is least reliable precisely when it matters most. `EXPERIENCE.md`'s "Speaker attribution unavailable" state only models a whole-call, binary condition (mono input → all turns unattributed, with a persistent inline note). There is no per-segment state for the case where diarization *does* run (mono input) but is uncertain for a specific span (e.g., cross-talk) — the existing `low`-confidence tag mechanism is scoped to sentiment/emotion-reading confidence (its own example reason is "utterance < 1.2s, overlapping cross-talk — insufficient acoustic signal," which is about signal quality for the emotion reading, not about whether the speaker label itself is trustworthy). As written, a mis-attributed or uncertain speaker label on a diarized (mono) call could be displayed with the same visual certainty as a confidently-diarized turn, even on a segment already flagged low-confidence for other reasons.
- **Location:** `EXPERIENCE.md` → State Patterns → "Speaker attribution unavailable"; `DESIGN.md` → Components → "Call row" (mono warning is call-level only, not segment-level).
- **Suggested fix:** Add a per-segment attribution-confidence indicator, distinct from the existing sentiment/emotion `low`-confidence and `disagreement` states (e.g., a muted speaker-label treatment or its own flag reason such as "speaker attribution uncertain — overlapping speech") for diarized (mono) calls, consistent with the product's existing "never hide uncertainty" pattern.
