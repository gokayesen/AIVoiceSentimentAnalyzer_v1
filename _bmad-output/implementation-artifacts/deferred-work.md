## Fixed outside any story's scope: acoustic RQ job timeout too low (2026-08-18)

Real-world bug report, not a code-review finding: a user's real MP3 upload (~10.8 min) reliably failed; a 6-minute trim of the same file failed identically. Root cause confirmed via live worker logs (`ml-service` container): `run_acoustic`'s RQ job hit `rq.timeouts.JobTimeoutException: Task exceeded maximum timeout value (180 seconds)` mid wav2vec2 forward pass. `run_ingest`'s `queue.get_acoustic_queue().enqueue(...)` call (the only acoustic-job enqueue call site in the codebase, confirmed by search) never overrode `job_timeout`, so RQ's own class-level default (`Queue.DEFAULT_TIMEOUT = 180`, `rq/queue.py`) applied. `run_acoustic` classifies every VAD-bounded segment sequentially on CPU (Story 1.3), so total job duration scales with segment *count*, not Call duration alone — the 6-minute trim still produced 147 VAD segments (pause-heavy source audio), reproducing the exact same failure as the longer original.

**Fix:** added `ACOUSTIC_JOB_TIMEOUT_SECONDS` (default `900`, env-overridable) to `ml-service/app/config.py`, passed explicitly as `job_timeout=` on the one acoustic-enqueue call site in `ml-service/app/pipeline/ingest/run.py`. Scoped to this one job only — RQ's global default and every other queue's timeout are untouched. `900` (5x the RQ default) is a deliberately generous empirical margin chosen to comfortably clear the worst segment-count case observed so far on this project's CPU-only target (AD-18), not a measured/tuned value. Covered by an updated assertion in `ml-service/tests/test_ingest.py` (`test_ingest_success_enqueues_acoustic_job_with_correct_path_and_call_id`); full `ml-service` suite + `ruff check` re-run green after the change; re-verified against a real upload of the same reproducing MP3 through the rebuilt Docker image.

**What this does not fix:** the underlying CPU-inference speed itself — this raises the ceiling, it doesn't make `wav2vec2` classification faster. A worst-case Call (near the 30-minute/AD-20 ceiling, pause-heavy, high segment count) could still exceed 900s on this hardware; if that's ever observed, the real fix is inference-side (batching segments per call instead of one-at-a-time, as already separately noted in the Story 1.5 review's deferred-work entry, or the standing Epic 1/3 action items on ML preflight and a standard Docker/dev-container performance baseline), not another timeout bump. Revisit if a Call is ever observed genuinely needing more than 900s.

## Fixed outside any story's scope: transcript RQ job timeout too low (2026-08-18)

Same real-world bug report as the acoustic entry above, discovered immediately after that fix shipped: the identical 244-segment Call that now cleared the acoustic stage died at the transcript stage instead, same failure signature (RQ's 180s class default). Root cause: `run_transcript`'s `transcribe_segment` runs faster-whisper's beam-search decode sequentially per VAD-bounded segment (Story 1.4) — same "duration scales with segment count, not Call duration" shape as acoustic — and `run_acoustic`'s `queue.get_transcript_queue().enqueue(...)` call (the only transcript-job enqueue call site in the codebase, confirmed by search) never overrode `job_timeout` either.

**Fix:** added `TRANSCRIPT_JOB_TIMEOUT_SECONDS` (default `2700`, env-overridable) to `ml-service/app/config.py`, passed explicitly as `job_timeout=` on the one transcript-enqueue call site in `ml-service/app/pipeline/acoustic/run.py`. Scoped to this one job only, same policy as the acoustic fix — RQ's global default and every other queue's timeout are untouched. `2700` was sized by the same method as `ACOUSTIC_JOB_TIMEOUT_SECONDS` (measured real per-segment rate × a segment-count headroom factor over the largest segment count observed on this project), not copied from it verbatim: a live 3-sample benchmark of `transcribe_segment` against this project's own model/hardware measured 5.39s–6.28s per segment (faster-whisper's beam-search decode is slower and more variable than wav2vec2's single forward pass), applied against the same ~1.6x segment-count headroom the acoustic 900s figure implies over its own 244-segment worst case (~390 segments × 6.3s/segment ≈ 2460s, rounded up to 2700s). Full rationale documented inline in `config.py`. Covered by an updated assertion in `ml-service/tests/test_acoustic_run.py` (`test_run_acoustic_success_enqueues_transcript_job_with_correct_path_and_call_id`); full `ml-service` suite (136 tests) + `ruff check` re-run green after the change; Docker image rebuilt.

**Verification status — incomplete:** unlike the acoustic fix, this one has not been confirmed end-to-end against a real successful transcript completion. The fresh-call verification attempt never reached the transcript stage at all — the acoustic stage itself failed again first, for a different reason. See the entry immediately below for what happened and why this fix's real-world transcript timing remains unobserved.

**What this does not fix:** identical caveat to the acoustic entry — this raises the ceiling, it doesn't make faster-whisper's decode faster. Revisit if a Call is ever observed genuinely needing more than 2700s.

## Known limitation identified outside any story's scope: RQ job-timeout headroom is not reliable under host CPU contention, and a hard-killed job leaves the Call stuck in "processing" forever (2026-08-19)

Surfaced while attempting to verify the transcript fix above end-to-end with a fresh upload of the same 244-segment MP3. Two distinct findings, kept together here because they were discovered in the same incident:

**1. The chosen timeout margins are not guaranteed headroom, just a generous empirical one.** The identical 244-segment acoustic workload that completed in 572s on its first run took >1135s on a later run — over 2x slower for the exact same input — and was hard-killed by RQ's work-horse monitor for exceeding the 900s budget (confirmed via direct Redis job-hash inspection: `timeout: 900`, `started_at`→`ended_at` spanning 1135s). Host `uptime` showed heavy CPU contention at the time (load averages up to 11.33 on a 4-core host — traced to an unrelated runaway VS Code helper process and concurrent Claude Code sessions, not this project's own containers). Any fixed `job_timeout` value can in principle be exceeded under sufficient host contention; 900s/2700s were never claimed to be hard ceilings (see both entries above's own "what this does not fix" caveats), but this is the first direct, reproduced evidence of the margin actually being blown in practice, not just a theoretical caveat.

**2. When that happens, the Call does not fail — it gets stuck in "processing" permanently.** RQ enforces `job_timeout` via an external work-horse monitor that sends `SIGKILL` to the job's subprocess once wall-clock duration exceeds the budget, independent of and in addition to the in-process `JobTimeoutException`. A `SIGKILL` bypasses all Python-level exception handling — including `run_acoustic`'s/`run_transcript`'s own outer `except Exception` block, which is the only code in this codebase (per AD-13, only the RQ worker writes `Call.status`) that would set `Call.status = "failed"`. That block never runs. The Call is left at whatever status it already had — `"processing"` — with no other job ever scheduled to run for it again. **Lifecycle invariant violated:** the implicit guarantee, relied on throughout AD-1's "never fail the Call, flag instead" design and the frontend's polling-based completion UX, that every Call eventually reaches a terminal status (`complete` or `failed`). That guarantee assumes every job either succeeds or raises a catchable Python exception; RQ's hard-kill-on-timeout mechanism is a real, reachable path that breaks the assumption outside of Python's control entirely. This is a distinct gap from "timeout value too low" — raising the timeout further reduces how often it's hit, but can never close the gap, since the hard-kill path exists at any finite timeout value.

Three Calls in the local dev database are currently stuck in `"processing"` as a direct result: `b97c231d`, `e12d1876`, `955edbd3`.

**User decision (2026-08-19):** recorded as a known limitation / technical debt only — no code change made in response to this finding. The project remains MVP READY per the 2026-08-17 verification; this does not reopen that verdict. The already-shipped `ACOUSTIC_JOB_TIMEOUT_SECONDS`/`TRANSCRIPT_JOB_TIMEOUT_SECONDS` fixes above are kept as-is (they are strict improvements over the prior 180s default regardless of this finding, not reverted). No new Epic/Story is opened for either finding. Revisit both together if this class of failure is ever observed affecting a real (non-test) user session, or as part of any future reliability-hardening pass — a real fix for finding 2 would need either a periodic reconciliation sweep (detect Calls stuck in `"processing"` past some staleness threshold and mark them `"failed"`) or RQ's own dead/stale-job detection, neither of which exists in this codebase today.
