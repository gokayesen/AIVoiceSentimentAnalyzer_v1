# Story 2.4: Analysis Dashboard — Summary Cells & Full Result View

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Analyst,
I want to view the full Analysis Result for a completed Call in one place,
so that I can see the overall picture before deciding whether to dig deeper.

## Acceptance Criteria

1. **Given** a completed Call, **When** the Analyst opens its Dashboard, **Then** they can view overall Sentiment, dominant Emotion, Confidence, Emotional Timeline, full transcript, and acoustic insights — all within this one surface, without leaving the tool (FR-12). **See Dev Notes "What this story's Timeline/transcript/acoustic panels do and don't render"**: the Timeline/transcript/acoustic panels required here are the *presence* of real, evidence-backed content — the low-confidence hatch/dashed-border, disagreement split-fill/dual-signal-panel, click-to-sync drill-down, and speaker-attribution labels are Story 2.5's scope, not this story's.
2. **Given** the Dashboard header area, **When** rendered, **Then** the Case strip shows filename, duration, queue name, and "analyzed N ago." **See Dev Notes "Known spec gap — no queue/routing concept exists"**: there is no queue field anywhere in the data model; "queue name" renders the same fixed `queue/session` placeholder AppHeader's breadcrumb already uses (Story 2.1 precedent), not fabricated per-call data. "Analyzed N ago" requires a real completion timestamp that does not exist yet on `Call` — Task 1 adds it.
3. **Given** the summary area, **When** rendered, **Then** it shows exactly four cells — Overall Sentiment, Dominant Emotion (+ Confidence), Secondary Signal, Segments Flagged — with the Confidence value in that cell unambiguously tied to the Dominant Emotion reading, per the Analysis Result's data contract (Story 1.6/1.8) — never a separate, generically-labeled confidence figure that could be read as belonging to Overall Sentiment instead.
4. **Given** the Secondary Signal cell, **When** no distinct-enough secondary reading exists (Story 1.9's "none" state), **Then** it displays "None flagged," never left empty/broken.
5. **Given** the Segments Flagged cell, **When** its count is greater than zero, **Then** it links to the first flagged segment; **when** zero, **Then** it displays plain, non-linked "0." **See Dev Notes "Segments Flagged counts low-confidence + disagreement, not the persisted column"**: the persisted `AnalysisResult.segments_flagged_count` only counts `disagreement_flag`, not low-confidence — this story computes the combined count client-side from `/timeline`'s already-live-computed per-segment flags, per EXPERIENCE.md's authoritative definition.
6. **Given** the main content area, **When** rendered, **Then** the full transcript panel and acoustic insights panel are both present in the two-column grid (~60%/~40%).
7. **Given** this story's components, **When** rendered, **Then** `badge-dot` is always adjacent to its text value, never alone, and all text/background pairs meet WCAG AA (4.5:1 text, 3:1 large-text/UI-boundary).
8. **Given** the Analyst is viewing a Call's Dashboard, **When** they click the `app-header` breadcrumb (established in Story 2.1), **Then** they are returned to the Session Call List — the normal, non-delete path back to the list from the Dashboard.
9. **And** per-segment drill-down interaction, low-confidence/disagreement states, and the dual-signal panel are Story 2.5's scope, not this story's.

**Traceability:** FR-12; NFR-1 (partial — evidence reachable, detail in 2.5); AD-16 (Confidence co-present with the Dominant Emotion reading, never shown unqualified); UX-DR3, UX-DR8, UX-DR18 (breadcrumb return-to-list), UX-DR20, UX-DR21 (WCAG AA token-sourced pairing).

**Dependency:** Story 2.1 (App shell, `AppHeader`'s `breadcrumbLabel`/`onBreadcrumbClick` stubs, DESIGN.md token system). Story 2.2 (`CallRow`'s `onSelectCall` stub, `callsApi.ts`'s `ApiError`/base-URL pattern). Story 2.3 (`ConfirmDialog` — **not** reused in this story, see Dev Notes "Story 2.3 AC2's Dashboard-delete gap is not resolved by this story"). Story 1.6 (fusion/`AnalysisResult`, Story 1.7 (`GET /calls/{call_id}/timeline`), Story 1.8 (low-confidence flagging), Story 1.9 (disagreement flagging) — all already implemented, read-only consumption plus the two additive backend endpoints/fields this story requires (Tasks 1-4).

## Dev Notes

### What this story's Timeline/transcript/acoustic panels do and don't render

Epic 2's own description frames Story 2.4 and 2.5 as a split: 2.4 is "the full Analysis Result... in one place" (presence, breadth), 2.5 is "select any point... and see its exact supporting evidence... low-confidence and disagreement moments impossible to miss" (interaction, specialized visual states). Concretely, in this story:

- **Timeline**: real segments, real base-variant colors/glyphs (neutral/positive/mixed/negative only), proportionally sized, non-interactive, no hatch/split-fill for flagged segments.
- **Transcript**: real turns, real text and timestamps, no speaker labels (no data exists), no low-conf/disagreement turn styling, no dual-signal panel.
- **Acoustic**: real call-level averages (four named features, real computed numbers), no narrative/comparison text, no timestamp-anchored highlighting.

This is not corner-cutting — every one of the excluded pieces requires either data this story doesn't fetch (per-segment acoustic anchoring) or interaction/synchronization logic epics.md explicitly assigns to Story 2.5 (AC392-411). Building any of it now would be scope creep into a story that hasn't been contexted yet, the same discipline every prior Epic 2 story applied to *its* forward references (Story 2.1 refusing to build upload, Story 2.2 refusing to build delete, Story 2.3 refusing to build the Dashboard).

### Known spec gap — no queue/routing concept exists

`epics.md` AC381/AC2-of-this-story requires the Case strip to show a "queue name." No `queue`/`routing` field exists anywhere in this codebase's data model — not on `Call`, not anywhere in Epic 1's upload endpoint, not in any migration. `mockups/analysis-dashboard.html`'s `"Returns & Refunds"` queue text is illustrative-only mockup flavor with no real backing data, exactly like `AppHeader`'s own already-shipped `'queue/session'` breadcrumb default (Story 2.1) — this product has no real multi-queue concept in its MVP scope at all (PRD is silent on queue/routing as a feature). This story renders the same fixed `"Session"` placeholder in the Case strip's queue field, consistent with that existing precedent, rather than fabricating a queue name with no data behind it. If a future story introduces real queue/routing data, both the Case strip and `AppHeader`'s breadcrumb default should be revisited together, not just one of them.

### Segments Flagged counts low-confidence + disagreement, not the persisted column

`AnalysisResult.segments_flagged_count` (persisted by `persist_fusion_results`, Story 1.6/1.9) only ever counts `disagreement_flag`-true segments — confirmed by reading `ml-service/app/pipeline/fusion/fuse.py`'s `reduce_call` (the only writer of this column). `low_confidence_flag` is deliberately **never persisted** (`web-api/app/routers/calls.py`'s `_low_confidence_flag` docstring: "Deliberately recomputed on every read against the *current* `LOW_CONFIDENCE_THRESHOLD`, never persisted... so this flag is a pure function... with nothing gained by storing it"). But `EXPERIENCE.md`'s Component Patterns section (the authoritative UX behavior spec) is explicit: *"Segments Flagged is a count (low-confidence + disagreement segments combined)."* These two facts mean the backend's persisted `segments_flagged_count` field is the **wrong number** for this cell — it would silently under-count by omitting every low-confidence-only segment. This story does not touch that persisted column at all; instead, Task 10 computes the combined count client-side from `/timeline`'s response, which already exposes both flags per segment, live-computed, on every read (Story 1.8/1.9's existing, already-tested behavior). Do not "fix" this by adding low-confidence persistence to `AnalysisResult` — that would violate `_low_confidence_flag`'s own documented rationale for staying non-persisted (a reconfigurable threshold must be able to change a Call's flagged segments on the next read, which persisting would break).

### Segments Flagged link target is a timeline segment anchor, not a transcript-turn anchor

The mockup's Segments Flagged cell links to a transcript turn (`href="#turn-0220"`), because the mockup illustrates the fully drilled-down Story 2.5 experience where a flagged segment and its corresponding transcript turn are already visually tied together. This story does not implement that segment↔turn time-range overlap matching (`AD-11`'s relationship, resolved server-side today only inside `ml-service`'s `fusion/overlap.py`, not exposed via any API) — building a client-side equivalent now would duplicate logic Story 2.5 may need to own differently once it adds real synchronization. Instead, Task 10's link targets the flagged Timeline segment directly (`#segment-{segment_id}`, matching the `id` Task 11's strip renders on each segment) — this satisfies AC5's literal text ("links to the first flagged segment") without inventing a turn-matching algorithm this story has no real use for beyond a single navigation link.

### Story 2.3 AC2's Dashboard-delete gap is not resolved by this story

Story 2.3's AC2 ("the same delete action is available [on the Dashboard], using the identical `confirm-dialog` component") was explicitly deferred with the reasoning "Story 2.4 can drop [`ConfirmDialog`] in unmodified when that story is built." This story's own AC set (epics.md lines 378-388) contains **zero** mention of delete, a confirm dialog, or any destructive action on the Dashboard — a real, verified fact, not an oversight in this analysis. Given every prior story in this Epic has strictly scoped itself to only what its own AC text requires (refusing to pull forward *or* leave behind adjacent concerns without an explicit AC anchor), this story does not wire delete into `AnalysisDashboard`, even though `ConfirmDialog` is trivially reusable and doing so would be low-risk. This leaves Story 2.3's AC2 as a **still-open, cross-story gap** with no future story in `epics.md` currently assigned to close it — flagged here explicitly (and in this story's completion notes) rather than silently left unaddressed, so the gap is visible to whoever plans the next epics revision, rather than discovered by accident later. This is a genuine planning question, not a technical one — it does not block this story's own implementation.

### Why local view-state, not a router

No `react-router-dom` (or any routing library) is installed (`frontend/package.json`, confirmed). Both Story 2.1 ("Do not add `react-router-dom`... Dashboard navigation is Story 2.4's concern") and Story 2.3 ("No... routing library — Story 2.4") explicitly deferred this exact decision here, treating it as a real choice this story must make, not a settled architecture mandate — `ARCHITECTURE-SPINE.md` itself is silent on routing (confirmed: no AD mentions it). `EXPERIENCE.md`'s own IA description frames this as "a two-surface product by design," with no deep-linkable URLs specified anywhere in either `DESIGN.md` or `EXPERIENCE.md`. Given `CallRow.onSelectCall` and `AppHeader.onBreadcrumbClick` were both already built (Stories 2.2/2.1) as bare callback stubs with no URL/history semantics implied, and there is no requirement anywhere (PRD, architecture, UX docs) for a shareable/bookmarkable Dashboard URL, local `useState` in `App.tsx` is the simplest implementation that satisfies every real AC — adding a router would be unrequested scope and a new dependency with nothing behind it. If a future story needs real deep-linking, that is the point to introduce one, not this story.

### Dominant Emotion cell color is driven by `overall_sentiment`, not a per-emotion guess

The mockup colors both the Overall Sentiment cell ("Negative") and the Dominant Emotion cell ("Frustration") with the same `.neg` (negative-red) class — i.e., the Dominant Emotion cell's color accent is the Call's overall *polarity*, not a bespoke per-emotion-label color mapping. This is the only interpretation backed by real API data: `overall_sentiment` is one of exactly four known polarity values (`negative`/`mixed`/`positive`/`neutral`, AD-4) with an existing token mapping already used by `CallRow`'s `badge-dot--${sentiment}` classes; `overall_emotion` has no polarity field of its own anywhere in the API contract (it is a free-form label from either taxonomy, per Story 1.6's Dev Notes on cross-taxonomy label spaces) and inventing an emotion→color table here would mean guessing at a mapping the backend has never defined. `secondary_signal_emotion` has the identical problem and is rendered in plain text for the same reason (Task 10).

### Partial-failure handling

`AnalysisDashboard` fires four independent requests on mount. `getCallStatus` failing is a hard failure (nothing in the Dashboard can render without it — Case strip and summary cells both depend on it). `getTimeline`/`getTranscript`/`getAcousticSummary` each failing independently degrades only that one panel (Timeline/Transcript/Acoustic respectively) — the rest of the Dashboard, including the Segments Flagged cell's dependency on `getTimeline`, should show a plain "unavailable" state for just that one piece rather than the whole page. This mirrors the general resilience posture Story 2.2/2.3 already established (a delete failure doesn't take down the whole row; an upload failure doesn't take down the whole list) applied to a page with multiple independent data sources for the first time in this codebase.

### Architecture compliance (non-negotiable)

- **AD-16** — every Sentiment/Emotion value this story renders is confidence-qualified (Dominant Emotion's Confidence sub-line, same cell) and evidence-linked (Overall Sentiment/Dominant Emotion trace to the real `AnalysisResult` row; Segments Flagged links to a real Timeline segment). The one exception — `no_speech_detected` — deliberately shows *nothing* rather than a fabricated zero/none result, which is the more AD-16-compliant choice, not a shortcut.

The DDL is hand-synced across both services' `db.py` (AD-7), same discipline as every other column in the `Call` table.
