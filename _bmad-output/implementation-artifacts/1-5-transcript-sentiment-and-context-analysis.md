# Story 1.5: Transcript Sentiment & Context Analysis

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Analyst,
I want the transcript analyzed for sentiment and conversational context,
so that the text signal contributes to the Analysis Result alongside the acoustic signal, without overriding it.

**Dependency:** requires Story 1.4's `TranscriptTurn` output (this stage runs only after transcript generation succeeds and produces at least the possibility of turns). Does not require Story 1.3 — Stories 1.3 and 1.4/1.5 remain independent signal producers, each consumed separately by Story 1.6 (Fusion).

## Acceptance Criteria

1. **Given** a Call has a completed transcript (Story 1.4's `TranscriptTurn` rows), **when** the transcript-sentiment filter runs, **then** it derives text-based Sentiment, Emotion, and keywords/context for every `TranscriptTurn`, using a small, fine-tuned or pretrained transformer classifier (RoBERTa/DistilBERT-family) — never a general-purpose LLM (AD-19, FR-7). [Source: epics.md#Story 1.5; AD-19]
2. **Given** this stage is implemented, **then** a general-purpose LLM (local or cloud) and any cloud LLM API must never be used — not for sentiment/emotion classification, and not for keyword/context extraction; the entire stage stays within the small-transformer / classical-NLP paradigm, never an "audio → STT → LLM → sentiment" pattern (AD-19). [Source: ARCHITECTURE-SPINE.md#AD-19]
3. **Given** the filter's native softmax confidence, **then** it is calibrated via temperature scaling before use — mirroring AD-9's acoustic-path pattern — and persisted as `text_confidence`; the raw uncalibrated softmax value is never persisted or used downstream (AD-9). [Source: ARCHITECTURE-SPINE.md#AD-9]
4. **Given** transcript Sentiment/Emotion output, **then** it is persisted as `text_sentiment`/`text_emotion`/`text_confidence`/`text_keywords` columns directly on `TranscriptTurn`, kept distinct from Acoustic Analysis output (`TimelineSegment.acoustic_emotion`/`acoustic_confidence`) at every layer — Sentiment and Emotion are never merged into one composite field (AD-15). [Source: ARCHITECTURE-SPINE.md#AD-15]
5. **Given** a `text_sentiment` value, **then** it is drawn from the same four-value polarity vocabulary AD-4 already established for the acoustic path (`negative`/`mixed`/`positive`/`neutral`) via this stage's own raw-Emotion→polarity lookup table, so Fusion (Story 1.6, AD-8) can compare polarities across modalities without a vocabulary mismatch. [Source: ARCHITECTURE-SPINE.md#AD-4, AD-8]
6. **Given** the transcript-sentiment filter fails, **when** this occurs, **then** the Call's transcript-analysis path is marked failed for this Call without failing the Call overall — `Call.status` is never written by this function, in any code path, consistent with Story 1.4's AD-1 divergence (never `run_ingest`/`run_acoustic`'s rollback-then-fail pattern). [Source: epics.md#Story 1.5; AD-1]
7. **And** inference runs locally only — no cloud API call is made for sentiment/emotion classification or keyword extraction (AD-14); model weights are fetched once (e.g. at Docker build time), never as a per-Call/per-request network call. [Source: ARCHITECTURE-SPINE.md#AD-14]
8. **And** the module has independently-runnable unit tests — `pytest ml-service/` passes with no live Redis/docker-compose (AD-21). [Source: epics.md#Story 1.5; AD-21]

## Dev Notes

### Previous story intelligence (Story 1.4)

- **Naming discipline, set up specifically for this story:** Story 1.4's Dev Notes explicitly flagged that "Story 1.5's future `TimelineSegment`/`TranscriptTurn` sentiment columns should use `text_*`/`transcript_*`" prefixes so Story 1.6's fusion output can later use unprefixed `sentiment`/`emotion` names. This story uses `text_*` on `TranscriptTurn` (Task 1) — do not deviate from this prefix.
- **`TranscriptTurn`/`TranscriptWord` schema (Story 1.4):** `TranscriptTurn` has no `segment_id` column by design (AD-11) — this story does not change that; it only adds nullable analysis-output columns to the existing table, the same way Story 1.3 added `acoustic_emotion`/`acoustic_confidence` directly onto `TimelineSegment`.
- **Model-caching pattern under RQ's forking `Worker` provides no real benefit** — already deferred three times (VAD, SER classifier, STT model; see `deferred-work.md`). Follow the same lazy-singleton pattern anyway for consistency (`sentiment.py`'s `_model`/`_get_model()`), but do not attempt to fix the underlying forking issue here — same accepted trade-off, now a fourth time.
- **Atomic batch-write pattern:** apply "compute everything in memory first, write once" from the start (Task 7) — Story 1.3 hit and fixed a real partial-write bug by not doing this initially; do not repeat that mistake.
- **Per-segment/per-turn error isolation:** Story 1.4's code review added this pattern to `run_transcript` *after* initially missing it (one segment's failure discarded the whole Call's other results). Build it into `run_text_sentiment`'s per-turn loop from the start (Task 7) — do not wait for a review to add it.
- **Rollback-before-failed-status pattern (`run_ingest`/`run_acoustic`) does NOT apply here**, same as it did not apply to `run_transcript`. `run_text_sentiment`'s failure semantics mirror `run_transcript`'s exactly (AD-1: never fail the Call for this stage).
- **RQ stage-chaining via import-path-string enqueue at the end of the previous stage's success path** — exact mechanism established in Stories 1.2 (web-api→ingest), 1.3 (ingest→acoustic), 1.4 (acoustic→transcript), continued here (transcript→text-sentiment). See Task 8.
- **Isolate a new enqueue call in its own nested try/except** — Story 1.4's code review found and fixed a real bug where `run_acoustic`'s new enqueue call shared its `except` block with the acoustic write, so a downstream queueing failure wrongly marked an already-successful operation as failed. Apply the isolated-try/except pattern from the start here (Task 8) — do not wait for a review to add it.

Document both choices and rationale in Dev Agent Record, same discipline as every prior story.

Verify the chosen text-sentiment checkpoint's actual `id2label` mapping and license against its real HF `config.json`/model card, not from memory (Task 5).

### Architecture compliance (non-negotiable)

- **AD-1 (voice-first, no bypass, and transcript-path failure isolation):** a transcript-sentiment-stage failure must never fail the Call — `Call.status` is untouched by `run_text_sentiment` in every code path, success or failure (Task 7). The acoustic signal (Story 1.3) remains independently valid regardless of this story's outcome, and Story 1.4's raw transcript remains independently valid even if this story's analysis fails.
- **AD-4 (shared four-value polarity vocabulary):** `text_sentiment` must be one of `negative`/`mixed`/`positive`/`neutral` — the same vocabulary AD-4 fixed for the acoustic path — via this story's own lookup table (Task 5). This is the single most likely point of accidental architecture violation if the classifier's raw labels are persisted directly without going through a mapping table.
- **AD-7 (consolidated ML/audio service, queue-only crossing):** `run_text_sentiment` lives in `ml-service`, invoked only via RQ job (never a direct in-process call) — the enqueue in Task 8 is intra-service stage-chaining via the job queue (AD-13), not a function call.
- **AD-9 (temperature-scaling calibration):** the classifier's native softmax confidence must be calibrated via temperature scaling before use (Task 5) — same mechanism, same "1.0 no-op placeholder pending real evaluation" honesty as `ACOUSTIC_TEMPERATURE`.
- **AD-13 (RQ/Redis orchestration, worker-only status writes):** `run_text_sentiment` never writes `Call.status`; only `run_ingest` and `run_acoustic` do.
- **AD-14 (local-only inference):** the text-sentiment model weights are pre-fetched at Docker build time (Task 9); no cloud API call at request time, for classification or keyword extraction.
- **AD-15 (Sentiment/Emotion stay distinct fields):** `text_sentiment` and `text_emotion` are separate columns, never merged into one composite field (Task 1).
- **AD-18 (CPU-only deployment):** no GPU-specific code paths; the classifier runs on CPU, same as every prior model in this service.
- **AD-19 (text-sentiment classifier is a small transformer, never an LLM):** this is the story's defining constraint — the classifier (Task 5) and the keyword extractor (Task 6) must both stay within the small-transformer/classical-NLP paradigm; no general-purpose LLM, local or cloud, anywhere in this stage.
- **AD-21 (independently-runnable tests):** `pytest ml-service/` must still pass with no live Redis/docker-compose — same `is_async=False` + `fakeredis` pattern as Stories 1.2–1.4.
