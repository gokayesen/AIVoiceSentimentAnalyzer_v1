# Story 1.9: Cross-Modal Disagreement Surfacing

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Analyst,
I want to be told when the acoustic and transcript signals disagree about a moment,
so that I can look closer instead of trusting a silently-blended number.

## Acceptance Criteria

1. **Given** a segment where the two modalities disagree in polarity and both exceed the **disagreement threshold** (AD-8; named alongside the low-confidence threshold in Architecture's Consistency Conventions as one of the two cross-cutting tunable thresholds — not a newly invented third value), **When** fusion evaluates it, **Then** an explicit per-segment disagreement flag is set and both signals are preserved and retrievable — never collapsed into one blended value (AD-8, FR-11).
2. **Given** the disagreement threshold, **Then** it is configured and documented as `disagreement_threshold`, kept separate from `low_confidence_threshold` (Story 1.8) and `acoustic_sanity_floor` (Story 1.3) — three distinct, independently-configured thresholds serving three distinct purposes (disagreement-trigger, flagging, invalidity), none interchangeable, none hardcoded in pipeline code.
3. **Given** a flagged segment, **When** retrieved via the API, **Then** it is distinguishable from a segment where both signals agreed.
4. **Given** the non-dominant modality's reading is distinct enough to report, **Then** it is retained and exposed as a "Secondary Signal" on `ANALYSIS_RESULT`, separate from the per-segment disagreement flag — never simply discarded (AD-8).
5. **Given** no distinct-enough secondary reading exists, **When** requested, **Then** the API returns an explicit "none" state, not empty/null.
6. **And** this logic has independently-runnable unit tests (AD-21).
7. **And** Story 1.7's timeline-retrieval endpoint already exposes the `disagreement flag` field by contract (defaulting to `false`/absent — see Story 1.7 Dependency note); this story populates its real value, requiring no API shape change.

**Dependency (from epics.md):** requires Story 1.6 (fusion — `fuse_segment`/`reduce_call`, which already wired the `disagreement_flag` field's *shape* as a hardcoded `False` no-op, and already wired the Secondary Signal's *full, real* computation) and Story 1.7 (the `GET /calls/{call_id}/timeline` endpoint, which already passes `disagreement_flag` through as a bare `bool()` read of the stored column). No new endpoint, no schema/DDL change, no `web-api` change — see "Critical context" below.

### What "disagree in polarity" means, concretely

`fused_sentiment`/`acoustic_sentiment`/`text_sentiment` are always one of exactly four values (`negative`/`mixed`/`positive`/`neutral`, AD-4) — this is the one place the two Emotion taxonomies (acoustic's 4-class, text's 28-class GoEmotions-derived set) are forced onto a shared, comparable vocabulary. This is *why* "disagree in polarity" is well-defined at all: comparing `acoustic_emotion` directly to `text_emotion` would be comparing across two different label spaces (not meaningful — "angry" vs. "disappointed" aren't directly comparable), but comparing `emotion_to_polarity(acoustic_emotion)` to `text_sentiment` (already a polarity, per Story 1.5's classifier contract) is. `fuse_segment` already computes `acoustic_sentiment` as a local variable before the dominance branch — reuse it; do not re-derive it a second time.

### Threshold semantics — "both exceed," not "either," not "the fused confidence"

AD-8's exact wording: *"When the two modalities disagree in polarity and both exceed a configurable confidence floor..."* — "both" refers to `acoustic_confidence` and `text_confidence`, the two raw per-modality calibrated confidences already available as `fuse_segment`'s own parameters, **not** the resulting `fused_confidence` (which is a self-weighted average of the two — checking that against the threshold would be a different, weaker condition: a very confident acoustic reading averaged with a very unconfident text reading could still produce a `fused_confidence` above threshold even though the text signal alone was too weak to trust for disagreement purposes). Requiring *both* raw values to individually clear the bar is what keeps a disagreement flag meaningful — a "disagreement" against a signal that was barely above noise isn't one worth surfacing to the Analyst.

### Awareness, not action: NaN confidence gap is pre-existing and out of scope

`deferred-work.md`'s Story 1.6 review entry already flags that `acoustic_confidence`/`text_confidence` are never validated as finite/non-NaN before use in fusion's arithmetic. This story's new disagreement comparison (`acoustic_confidence > DISAGREEMENT_THRESHOLD`) inherits the same gap — a NaN confidence would make this comparison silently `False` (IEEE754: all NaN comparisons are `False`), just like it already silently bypasses `ACOUSTIC_SANITY_FLOOR`'s check in Story 1.3. This is not a new defect this story introduces; it is the same pre-existing, already-deferred gap surfacing in one more downstream consumer.
