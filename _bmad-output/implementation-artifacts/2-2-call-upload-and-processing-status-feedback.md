# Story 2.2: Call Upload & Processing-Status Feedback

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Analyst,
I want to upload a Call from the Session Call List and watch it move through validation and processing,
so that I know exactly what's happening to my upload without leaving my queue.

## Acceptance Criteria

1. **Given** the Session Call List, **When** the Analyst clicks "+ Add call" or uses the file picker, **Then** a native file-selection dialog opens — file picker is the required, always-available path.
2. **Given** the Session Call List, **When** the Analyst drags a file onto it, **Then** the same upload flow triggers — drag-and-drop is a progressive enhancement, not the only path.
3. **Given** a file is submitted, **When** it is sent to Epic 1's upload endpoint (Story 1.1), **Then** a new row appears in the list in a "validating" state (FR-1).
4. **Given** the upload fails validation (per Story 1.1's API), **When** the error is returned, **Then** the row shows the specific validation error and a retry/re-upload action — it does not disappear or block the rest of the list (FR-2).
5. **Given** validation passes, **When** the Call is queued and picked up by the worker (Story 1.2), **Then** the row shows a "processing" status distinct from "validating" and "complete" (FR-3) — the Analyst can keep working with other Calls; processing is never full-screen blocking.
6. **Given** processing fails (Story 1.2/1.3), **When** the row updates, **Then** it states the Call could not be analyzed with a clear, non-blaming message and a retry action — never shown as if it silently completed (FR-3).
7. **Given** a Call reaches `complete`, **When** the Analyst views its row, **Then** the row is selectable (full-row hit target, click or keyboard Enter/Space) and opens the Analysis Dashboard.
8. **Given** a Call row, **When** rendered, **Then** it shows filename, Sentiment/Emotion + Confidence with `badge-dot`, and duration — populated once `complete`; earlier states show status text in place of result fields.
9. **And** this story only consumes Epic 1's existing upload/status API (Stories 1.1, 1.2) — no new backend endpoint or status semantics introduced. **See Dev Notes "Known spec gaps" item 1 before starting Task 1**: as literally written this AC is not achievable, because Epic 1 never actually shipped a status-polling endpoint capable of distinguishing `processing` from `failed` or returning `complete` results — this story adds the smallest possible correction, not new status semantics or a new status-*writer*.

**Traceability:** FR-1, FR-2, FR-3; UX-DR7, UX-DR8, UX-DR11, UX-DR18.

**Dependency:** Story 2.1 (App shell, `SessionCallList` page, DESIGN.md token system — all reused, not rebuilt). Story 1.1 (`POST /calls`), Story 1.2 (async status lifecycle: `queued`→`processing`→`complete`/`failed`, written only by ml-service's RQ worker per AD-13). Story 1.6 (fusion — `AnalysisResult` row, needed for AC8's Sentiment/Emotion/Confidence). This story does **not** depend on Story 1.7/1.8 (`GET /calls/{call_id}/timeline`) — that endpoint is Dashboard territory (Story 2.4/2.5), not used here.

## Dev Notes

### Known spec gaps — read this before touching `web-api`

1. **AC9 ("no new backend endpoint") is not achievable as literally written — Epic 1 never shipped a status-polling endpoint.** Confirmed by reading `web-api/app/routers/calls.py` end-to-end: the only three endpoints are `POST /calls` (returns `{call_id, status: "queued"}` once, at upload time only), `GET /calls/{call_id}/timeline` (200 only once `status == "complete"`; otherwise a 409 `CALL_NOT_COMPLETE` whose `message` string embeds the *current* status as free text but whose `error_code` is identical — `"CALL_NOT_COMPLETE"` — for `queued`, `processing`, **and** `failed` alike, so a client cannot structurally distinguish "still working" from "processing failed" without parsing a human-readable sentence), and `DELETE /calls/{call_id}`. There is no way to satisfy AC5/AC6/AC8 (distinguish `processing` from `failed`; show Sentiment/Emotion/Confidence once `complete`) against this API surface. Story 2.1's own Dev Notes already flagged half of this gap ("Also note, for whoever picks up Story 2.2... no CORS middleware") but not this half. **Resolution (Task 1):** add the smallest possible correcting endpoint, `GET /calls/{call_id}`, built entirely from functions and patterns that already exist — `db.get_call()`'s own docstring literally anticipates this ("read-only Call lookup for the timeline-retrieval endpoint (status gate) **and any future results endpoint**"), and the new `get_analysis_result()` reader is a one-line copy of the existing `get_timeline_segments()` pattern. This is a minimal, architecture-consistent correction, not a scope expansion — it changes nothing about *who writes* `Call.status` (still exclusively ml-service's RQ worker, AD-13 untouched) or introduces any new status value/semantics (still exactly `queued`/`processing`/`complete`/`failed`, Story 1.2's existing state machine). If in doubt about whether this was the right call, the alternative — parsing the `CALL_NOT_COMPLETE` error's free-text `message` string to distinguish `processing` from `failed` — was considered and rejected as fragile (string-matching production behavior against a message intended for human/log consumption, not machine parsing).
2. **The mockup has no visual reference for `validating`/`processing`/`failed` rows.** `mockups/session-call-list.html` renders only five `complete`-state rows (per EXPERIENCE.md line 32, "the Upload surface's transient states... are spine-only — simple row-level text/status changes that don't need a dedicated visual mock"). This story's non-complete row states are therefore built from EXPERIENCE.md's State Patterns prose (lines 74–77) and DESIGN.md's token system directly, not transcribed from any HTML — there is nothing to "get wrong" against a mock here because none exists; the risk is instead under-specifying these states relative to the always-fully-specified `complete` row. Tasks 6/8 spell out exactly what each state must render for this reason.
3. **`overall_sentiment`'s stored values are an exact, lowercase match to `badge-dot`'s DESIGN.md variant keys — verified, not assumed.** Grepped `ml-service/app/pipeline/acoustic/taxonomy.py` and `ml-service/app/pipeline/transcript/sentiment_taxonomy.py`: every taxonomy lookup table maps onto exactly `"negative"`/`"positive"`/`"neutral"`/`"mixed"` (lowercase), identical to `DESIGN.md`'s `components.badge-dot.variants` keys and to `web-api`'s existing `TimelineSegment.fused_sentiment` values (already visible in `test_timeline.py`'s fixtures, e.g. `fused_sentiment="negative"`). No sentiment-to-badge-color mapping table is needed in the frontend — the CSS class can be `badge-dot--${sentiment}` directly. Do capitalize for the *displayed text* only (`"Negative"`, not `"negative"`) — the mock's rendered copy is capitalized even though the underlying data is lowercase.

### Retry semantics

Neither the epics AC text nor EXPERIENCE.md specifies retry mechanics beyond "a retry/re-upload action" (AC4) and "a retry action" (AC6) existing. This story's chosen behavior, consistent across both failure origins: keep the original `File` object on the `SessionCall` row (Task 3) and have "Retry" re-invoke the exact same `submitFile` upload path used for a first attempt — this reuses one code path for both "first try" and "retry," rather than inventing a second, parallel retry-specific flow. A validation failure (AC4) and a processing failure (AC6) therefore look identical from the Retry button's perspective; only the row's error copy differs (Task 6, "Processing-failure copy" below).

### One `failed` state, two failure origins

`SessionCall.state` has a single `'failed'` value covering both a validation rejection (AC4, `POST /calls` returned a 4xx with a real `error_code`/`message`/`next_step`) and a processing failure (AC6, `GET /calls/{call_id}` returned `status: "failed"`, with no structured reason available from the backend). A second enum value was considered and rejected: both cases render identically (filename + message + next-step-or-generic-copy + Retry), the only difference is *where the message text comes from*, which the `errorMessage`/`errorNextStep` fields already carry regardless of origin. Do not add a `failureOrigin` field unless a real behavioral difference between the two surfaces during implementation.

### Processing-failure copy

Story 1.2/1.3 never persist a human-readable failure reason on a `failed` Call (confirmed: `Call` table has no `failure_reason`/`error_message` column in `web-api/app/db.py`'s DDL, and ml-service's RQ worker only ever writes `status`). AC6 requires "a clear, non-blaming message" regardless — since the backend has nothing to pass through, author fixed UI copy for this case, e.g. `"This call could not be analyzed."` as the message and `"Try uploading it again."` as the next step (exact wording is this story's own choice — keep it short, non-blaming, no exclamation points, per EXPERIENCE.md Voice and Tone). This is different from the validation-failure case (AC4), where the message/next-step *are* real backend passthrough text (`errors.py`'s specific per-rule copy) — do not blend the two into one generic string.

### Frontend↔backend base URL

`docker-compose.yml` maps `web-api` to host port `8000` and `frontend` to host port `3000` (both `"container:host"`-identical mappings). The browser executing the frontend's JS always runs on the *host* machine (or the developer's own machine in `npm run dev`), never inside the `frontend` container's network namespace — so from the browser's point of view, `web-api` is reachable at the host's `localhost:8000` in every scenario this project supports (dev server, or the full docker-compose stack), with no container-to-container DNS name (`http://web-api:8000`) ever being the right answer for *client-side* `fetch` calls. `http://localhost:8000` as a hardcoded default, overridable via `VITE_API_BASE_URL` (Vite's standard `import.meta.env` mechanism, build-time-only — consistent with this being a static-build-then-`serve` deployment per Story 2.1's Dockerfile, not a runtime-configurable server), is therefore correct without needing a Vite dev-server proxy or an nginx reverse-proxy layer, neither of which any existing doc calls for.

### CORS configuration

Add `CORSMiddleware` to `web-api/app/main.py` with `allow_origins=["http://localhost:3000", "http://localhost:5173"]` (the Docker-served frontend and the Vite dev-server default port, respectively — `5173` is Vite's own hardcoded default per its docs, not this project's choice), `allow_methods=["GET", "POST", "DELETE", "OPTIONS"]` (matches the router's actual verbs — no `PUT`/`PATCH` exist), `allow_headers=["*"]`. No `allow_credentials=True` — this product has no auth/cookies (PRD §2.3), so there is nothing credential-bearing to allow, and turning it on would needlessly narrow the `allow_origins` wildcard rules browsers enforce for credentialed requests. Do not use `allow_origins=["*"]` even though it would also work here (no credentials involved) — an explicit list is one line longer and costs nothing, and is the more defensible default for anyone reading this file later without the "no auth" context fresh in mind.
