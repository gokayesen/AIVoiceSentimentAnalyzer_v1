# Story 2.5: Timeline, Transcript & Acoustic Evidence Drill-Down (low-confidence + disagreement states)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Analyst,
I want to select any point on the Emotional Timeline and see its exact supporting evidence, with low-confidence and disagreement moments impossible to miss,
so that I can judge each moment on real evidence instead of a bare label.

## Acceptance Criteria

1. **Given** a completed Call's Dashboard, **When** the Timeline renders, **Then** it is a chronologically-ordered strip covering the full Call, each segment showing its fill color and fixed glyph (`–`/`◆`/`▼`/`▲`). **See Dev Notes "Timeline glyph-color fix"**: the neutral variant's glyph currently renders white (a pre-existing Story 2.4 bug) instead of the dark `--color-text` DESIGN.md specifies — this story fixes it while already touching this file's variant styling.
2. **Given** a Low-Confidence segment, **When** rendered, **Then** it shows the hatch pattern, dashed border, and `?` glyph — never confusable with a "Neutral" reading (FR-14).
3. **Given** a Disagreement segment, **When** rendered, **Then** it shows the split-fill and `⚠` glyph.
4. **Given** the Analyst selects a Timeline segment (click or arrow-key when focused), **When** selected, **Then** the transcript panel scrolls to the corresponding turn and the acoustic panel highlights the relevant metrics — one action synchronizes all three panels (FR-13). **See Dev Notes "Selection model"**: a single `selectedSegmentId` owned by `AnalysisDashboard` drives all three panels; clicking a transcript turn is also wired to set it (see "Turn selection is uniform, not flagged-only"), satisfying UX-DR4 as a strict subset of this AC's own synchronization requirement.
5. **Given** a transcript turn, **When** rendered, **Then** it shows `default`, `low-confidence` (dashed left border, `low` tag + stated reason), or `disagreement` (solid negative left border, `conflict` tag, embedded Dual-signal panel) matching its segment's state. **See Dev Notes "Turn state is derived from overlapping segments"**: `TranscriptTurn` has no flag columns of its own (AD-11) — state is computed client-side from the turn's time-range overlap with `/timeline`'s already-flagged segments.
6. **Given** a `disagreement` turn, **When** rendered, **Then** it contains the Dual-signal panel — two fixed-labeled halves ("Text signal"/"Tone signal"), each with its own value+confidence — never collapsed to one blended number.
7. **Given** the acoustic panel displays a metric, **When** rendered, **Then** it names an actual acoustic feature (pitch/F0, energy, speaking rate, or pauses/voice-activity — never a generic "acoustic score"), shows the measured value, and is anchored to a specific transcript timestamp. **See Dev Notes "Acoustic panel: aggregate by default, per-segment on selection"**: Story 2.4's call-level aggregate view stays the default (nothing selected); selecting a segment swaps it for that segment's own four metrics, anchored by the segment's own time range.
8. **Given** a transcript turn whose Analysis Result speaker-attribution data indicates the `uncertain` state (per the predefined speaker-attribution contract — see Architecture AD-6/AD-10), **When** rendered, **Then** its Speaker label shows the `uncertain` variant (dotted underline) — visually distinct from the transcript-turn `low-confidence` dashed border, so the two uncertainty axes are never conflated. This story renders the UI contract against that existing data shape only; populating real diarization values into that contract is Epic 3's responsibility, not a dependency this story waits on. **See Dev Notes "Speaker-attribution data gap"**: no such data shape actually exists anywhere in this codebase's schema yet — this story adds frontend-only optional fields and a `SpeakerLabel` component that Epic 3 will later populate, unreachable with real data until then.
9. **Given** every Timeline segment, **When** accessed by a screen reader, **Then** it carries an accessible name stating time range, reading, and — when applicable — flagged state/reason.
10. **Given** the transcript panel, **When** used by a screen reader, **Then** it is the guaranteed complete non-visual equivalent to the Timeline. **See Dev Notes "Known accessibility gap carried to Story 2.7"**: an unflagged turn has no explicit confidence/sentiment text of its own today — flagged here as a genuine open gap for Story 2.7 (cross-cutting a11y verification) to close, not silently resolved or silently ignored.
11. **Given** every Timeline segment, **When** focused via keyboard, **Then** it is individually focusable with the `focus-ring` treatment.
12. **And** this story does not implement the whole-Call "Speaker attribution unavailable" state or Epic 3's diarization data itself — only the UI contract Epic 3 will populate.

**Traceability:** FR-9 (UI realization), FR-11 (UI realization), FR-13, FR-14; NFR-1; AD-16 (evidence linkage — timeline/transcript/acoustic synchronization is the evidence-linked drill-down AD-16 requires); UX-DR2, UX-DR4, UX-DR5, UX-DR6, UX-DR10, UX-DR12; partial UX-DR16 (screen-reader/focus items owned here).

**Dependency:** Story 2.4 (`AnalysisDashboard` shell, base `Timeline`/`TranscriptPanel`/`AcousticPanel` components, `callsApi.ts`'s `getTimeline`/`getTranscript`/`getAcousticSummary`, `sentimentColorVar`/`sentimentGlyph`, `capitalize`, `formatDuration`) — this story extends all of these in place, does not replace them. Story 1.7/1.9 (`/timeline`, low-confidence + disagreement flags). Story 1.4/1.5 (`/transcript`'s `text_sentiment`/`text_confidence`, already returned per Story 2.4 Task 3's forward-looking design specifically for this story). Story 1.3 (`AcousticEvidence` rows, one per `TimelineSegment`, AD-3). Epic 3 (`backlog`) — speaker-attribution data; this story builds the UI contract only, per AC8.

## Dev Notes

### Selection model: one `selectedSegmentId`, three synchronized panels

`AnalysisDashboard` owns a single `selectedSegmentId: string | null`. `Timeline` and `TranscriptPanel` both receive it plus an `onSelectSegment` setter; `AcousticPanel` receives the resolved `TimelineSegmentResponse` object itself (not just the id) since it needs the segment's own fields to render. No component maintains its own parallel "selected" state — this avoids the exact kind of state-sync bug class Story 2.4's own review found once already (stale-response guard on unmount). There is no separate persistent "selected" visual style beyond the browser's native focus indicator on the now-`tabIndex={0}` segment/turn elements — the mockup's `.demo-focused` box-shadow is literally the `focus-ring` treatment applied to a Timeline segment (DESIGN.md `components.focus-ring`, `applies-to: ... timeline-segment (individually focusable) ...`), not a separate "selected" token; the three synchronized panels (transcript scroll position, acoustic panel content) already provide the analyst-visible feedback that a selection happened.

### Turn state is derived from overlapping segments, not stored on `TranscriptTurn`

`TranscriptTurn` has no `disagreement_flag`/`low_confidence_flag`/`flag_reason` columns of its own, by design (AD-11: a `TranscriptTurn` relates to `TimelineSegment` only via time-range overlap, never a scalar FK — confirmed in `web-api/app/db.py`'s own DDL comment: "Deliberately NO `segment_id` column"). This story computes each turn's visual state client-side via `findOverlappingSegment` (Task 2), reusing data both `/timeline` and `/transcript` already return — no backend change beyond Task 1's additive fields is needed for this. A turn overlapping more than one segment (the many-to-many relationship AD-11 describes) uses the documented flagged-priority rule in `findOverlappingSegment`, not an attempt to render multiple simultaneous states on one turn (no such visual pattern exists anywhere in DESIGN.md).

### Speaker-attribution data gap — building a UI contract nothing populates yet

AC8 says this story "renders the UI contract against that existing data shape only" — but no such data shape exists: `web-api/app/db.py`'s `_CREATE_TRANSCRIPT_TURN_TABLE` (confirmed, full DDL read) has no speaker/attribution column of any kind, and `ml-service` has never written one (Epic 3, which owns this data per AD-2/AD-6, is still `backlog`). AD-10 *mandates* that speaker-attribution confidence eventually co-exist with Sentiment/Emotion confidence on the same `TranscriptTurn` row, but "eventually" has not happened yet. This story's honest interpretation, consistent with Story 2.4's "Known spec gap — no queue/routing concept exists" precedent: add `speaker_label?: string | null` / `speaker_uncertain?: boolean` as **optional, frontend-only** fields on `TranscriptTurnResponse` (Task 7) and build the `SpeakerLabel` component (Task 9) + its conditional wiring in `TranscriptPanel` (Task 4) — real code, real tests, zero backend dependency — but it will never actually render with real data until some future Epic 3 story adds the matching DB column(s) and starts populating them. Do not add a backend DB column or endpoint field for this in this story — that is explicitly out of scope (AC8's own text: "populating real diarization values into that contract is Epic 3's responsibility, not a dependency this story waits on").

### Timeline glyph-color fix (pre-existing Story 2.4 bug, fixed here because this file is already being touched)

`Timeline.css`'s `.timeline__glyph` currently hardcodes `color: var(--color-panel)` for every variant. This is correct for `positive`/`mixed`/`negative` (white glyph on a saturated fill) but wrong for `neutral` (DESIGN.md: `neutral: 'fill {colors.neutral-signal}; glyph "–" ..., foreground {colors.text}'` — dark, not white; confirmed against the mockup's own `.seg.neutral .glyph { color: #12181F; }`, `--color-text`'s exact hex). This story's Task 3 fixes it as part of adding the two new variants' own glyph colors, since all of this lives in the same small CSS block being modified anyway — not a separate, out-of-scope bug-hunt.

### Acoustic panel: call-level aggregate by default, per-segment on selection

Story 2.4's `AcousticPanel` only ever showed the Call-level average (`getAcousticSummary`). AC7 requires a metric "anchored to a specific transcript timestamp," which a Call-level average structurally cannot be. Rather than replacing the aggregate view (Story 2.4's own AC1/AC6 still require acoustic insights to be visible without selecting anything first), this story adds a second, selection-driven mode: when a segment is selected, its own `AcousticEvidence` row (now returned by `/timeline`, Task 1) replaces the aggregate display, anchored by that segment's own time range. Nothing is fetched newly for this — Task 1 piggybacks the per-segment acoustic fields onto the `/timeline` response `AnalysisDashboard` already fetches, so there is no new loading/error state to design.

### Turn selection is uniform, not flagged-only

EXPERIENCE.md's Interaction Primitives states generally that "every clickable row/turn is also a focusable, keyboard-activatable element" — not scoped to flagged turns specifically. UX-DR4 additionally calls out that "clicking a flagged turn synchronizes the acoustic panel." This story makes **every** turn with an overlapping segment clickable/focusable and wires it to the same `onSelectSegment` Timeline segments use — flagged-turn-click-syncs-acoustic (UX-DR4) is then a strict subset of this uniform behavior, not a second code path to build and maintain separately. A turn with no overlapping segment at all stays non-interactive (nothing to select).

### Backend scope: one endpoint extended, zero new endpoints

Every backend change in this story is additive fields on the already-existing `GET /calls/{call_id}/timeline` (Task 1) — no new endpoint, no new table, no write-path change anywhere. `ml-service` is untouched (it already writes `acoustic_emotion`/`acoustic_confidence` on `TimelineSegment` and `AcousticEvidence` rows per segment — Stories 1.3/1.6 — this story only makes `web-api` return data it already has). This mirrors Story 2.4's own "smallest additive surface" discipline (its Task 1-4 additions), applied here to a single endpoint instead of two new ones, because the data this story needs (per-segment acoustic values, tone-signal fields) already sits one join away from data `get_timeline` already reads.

### Architecture compliance (non-negotiable)

- **AD-16** — every value this story renders (Dual-signal panel's two halves, per-segment acoustic metrics, Timeline segment accessible names) stays confidence-qualified and evidence-linked; the Dual-signal panel's explicit purpose is to *prevent* AD-16 violations by never collapsing two disagreeing signals into one unqualified number.
- **AD-11** — the client-side `overlaps`/`findOverlappingSegment` utility (Task 2) is this story's own implementation of AD-11's stated time-range-overlap relationship, not a redefinition of it; it must never clip or re-derive `TranscriptTurn`/`TimelineSegment` boundaries themselves (both stay exactly as returned by the API).
- **AD-10** — this story's Dual-signal panel keeps Sentiment/Emotion confidence (text signal) and the acoustic/tone signal's own confidence as two visibly separate values, never combined into one score — the literal UI realization of AD-10's "two independent confidence axes must never be conflated" rule. The `SpeakerLabel` component (Task 9) is deliberately built with its own distinct visual language (dotted underline) so a future Epic 3 story populating real speaker-attribution confidence data does not conflict with this axis either.
- **AD-3 / AD-8** — the per-segment acoustic fields this story surfaces (Task 1) are read-only pass-throughs of data `ml-service`'s acoustic/fusion stages already compute and persist (Stories 1.3/1.6) — no new computation, no new confidence/calibration logic is introduced anywhere in this story.
