# Story 2.6: No-Certainty Language, Standing Disclaimer & Terminology Discipline

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Analyst,
I want every reading phrased as an estimate, not a fact, with a constant reminder that I am the final reviewer,
so that I never mistake the tool's output for a settled verdict.

## Acceptance Criteria

1. **Given** every Dashboard, **When** it renders, **Then** it shows the standing disclaimer bar under the summary cells, with the fixed, non-dismissible, non-alert-styled copy: "Model output — acoustic + lexical estimate, not a determination. Analyst review required before action." — identical on every Call (NFR-4). **See Dev Notes "Disclaimer bar placement"**: the bar renders only in the has-a-result branch (immediately after the summary row, before the Emotional Timeline section-label — exact position confirmed against `mockups/analysis-dashboard.html`), not in the `no_speech_detected` branch, where no summary cells or Model output exist to disclaim in the first place.
2. **Given** any Sentiment/Emotion reading anywhere in the Dashboard, **When** displayed, **Then** it is presented as an estimate, not a factual determination, and is evidence-linked where applicable — never a flat assertion of settled fact (e.g., never "the customer is frustrated") (FR-15; NFR-2 confidence honesty — this AC does not require numeric/probabilistic phrasing everywhere, only that certainty is never asserted). **See Dev Notes "Single-modality disclosure gap"**: `single_modality_flag` (already computed and returned by `GET /calls/{call_id}` per Story 1.6/AD-1/AD-8) has never been surfaced in the Dashboard by any prior Epic 2 story — a single-signal (acoustic-only) result currently renders visually identical to an ordinary two-signal fused result, which is exactly the "never presented as an ordinary two-signal fused result" case AD-1/AD-8 forbid. This story closes that gap for the Call-level flag (frontend-only; no backend/API change).
3. **Given** a field labeled "Sentiment," **Then** it always shows a polarity; **given** a field labeled "Emotion," **Then** it always shows an Emotion value — no UI string uses one to mean the other (NFR-3). **See Dev Notes "Terminology audit result"**: already correct everywhere in the current codebase (verified — `AnalysisDashboard.tsx`'s Overall Sentiment/Dominant Emotion cells, `CallRow.tsx`'s sentiment/emotion line, `Timeline.tsx`'s `fused_sentiment`-keyed glyph); this AC's task is a locking regression test, not a code fix.
4. **Given** any `low`/`conflict` tag, **When** rendered, **Then** it is never shown bare — always paired with its stated reason. **See Dev Notes "Tag-pairing audit result"**: already correct and already covered by existing tests from Story 2.5 (`TranscriptPanel.test.tsx` — the `low` tag's reason comes from the segment's always-non-null `flag_reason`; the `conflict` tag's "reason" is the adjacent Dual-signal panel itself, per `mockups/analysis-dashboard.html`'s own ground-truth markup, which shows no separate reason sentence next to `CONFLICT`). No code or new test required for this AC.
5. **Given** a Call without available speaker attribution, **When** its Dashboard renders, **Then** it states this plainly ("Mono input — turns unattributed") — this AC establishes the copy contract; Epic 3 supplies the actual data. **See Dev Notes "Whole-Call speaker-attribution-unavailable note"**: implemented as a Dashboard-level note above the Transcript panel, computed from whether *any* transcript turn carries a `speaker_label` (Epic 3's real data path — currently never populated, so this note renders on every real Call today, by design, same "honest until Epic 3 lands" posture Story 2.5 documented for `SpeakerLabel`).
6. **Given** any accuracy, performance, or reliability claim, **When** it would be surfaced anywhere in the product (in-app copy or documentation), **Then** it must state what it was measured against (dataset, method, conditions); for MVP, this means no aggregate or unqualified accuracy/performance claim is displayed anywhere in the product — the only numbers shown are per-Call Confidence values, already governed by the certainty AC above (NFR-5). **See Dev Notes "Terminology audit result"**: audited, no violation found — no code change.
7. **Given** any Dashboard copy, **When** authored, **Then** it uses no exclamation points, no "Great news!" framing, no anthropomorphizing language. **See Dev Notes "Terminology audit result"**: audited (`grep` pass across `frontend/src`), no violation found — no code change; this story's own two new copy strings (Task 2, Task 4) are written to the same standard.
8. **Given** the disclaimer bar and every flag-reason string, **When** rendered, **Then** they are real text, never image/icon-only. Applies equally to this story's two new notes (mono-input, single-modality) — all four render as plain DOM text nodes, queryable by a screen reader and by `@testing-library`'s `getByText`.
9. **And** this story governs copy/language only — it does not alter Story 2.4/2.5's visual/interaction contracts (Timeline variants, selection/sync wiring, Dual-signal panel, Speaker label). No `web-api` or `ml-service` change of any kind — every field this story surfaces (`single_modality_flag`, transcript turns' absent `speaker_label`) is already returned by an existing endpoint.

**Traceability:** FR-15; NFR-2, NFR-3, NFR-4, NFR-5; AD-1, AD-8 (single-modality disclosure — gap identified during this story's creation, see AC2/Dev Notes), AD-16 (human-in-the-loop framing); UX-DR14, UX-DR15; partial UX-DR16 (real-text requirement owned here).

**Dependency:** Story 2.4 (`AnalysisDashboard` shell — case-strip, summary row, `status.single_modality_flag` already on `CallStatusResponse`) and Story 2.5 (`Timeline`/`TranscriptPanel`/`DualSignalPanel`/`SpeakerLabel`, `TranscriptTurnResponse.speaker_label`) — this story extends `AnalysisDashboard.tsx` only; it does not modify either story's own components. No dependency on Epic 3 (still `backlog`) — this story's speaker-attribution copy is the same "build the contract, not the data" posture Story 2.5 already established for `SpeakerLabel`.

## Dev Notes

### Disclaimer bar placement

`mockups/analysis-dashboard.html` (the ground-truth 1:1 visual reference — EXPERIENCE.md: "the spine ... always wins on conflict with a mock," but no conflict exists here) places `.disclaimer` as a direct sibling immediately after `.summary-row` and immediately before `.section-label` ("Emotional Timeline") — never inside or before the summary cells. The mock has no rendered example of the `no_speech_detected` state (Story 2.4's own addition, after the mock was built) — that branch has no summary cells, no Sentiment/Emotion/Confidence values, and nothing resembling "Model output" to disclaim. Rendering the fixed disclaimer text there would be copy for a result that doesn't exist, which is arguably its own small no-certainty-language violation (implying there's a qualified estimate to disclaim when there is none). This story's own decision, made explicitly here rather than left for the dev agent to guess: the disclaimer bar renders **only** in the has-a-result branch, at the mock's exact structural position. This is a real design decision, not an oversight — documented so a future reviewer doesn't flag it as a missed AC.

### Single-modality disclosure gap

Found during this story's creation, not previously called out by any Epic 2 story: `GET /calls/{call_id}` (`web-api/app/routers/calls.py`, confirmed by direct read) already computes and returns `single_modality_flag` on `CallStatusResponse` (Story 1.6's fusion output — set when transcript analysis failed/was unavailable and fusion proceeded on the acoustic signal alone, per epics.md line 242 / AD-1 / AD-8's explicit rule: "outputs the acoustic-emotion signal alone with an explicit single-modality flag ... never presented as an ordinary two-signal fused result"). No prior Epic 2 story (2.1-2.5) ever rendered this field — `grep -rn "single_modality" frontend/src` before this story's changes shows it only in the type definition and one test fixture, never in JSX. A single-modality Call's Dashboard today looks pixel-identical to an ordinary two-signal fused result, which is precisely the outcome AD-1/AD-8 forbid. This story closes the gap for the Call-level flag only (Task 3) — zero backend change, since the field already exists on an already-fetched response. The **per-segment** `single_modality_flag` column (`TimelineSegment.single_modality_flag` in `web-api/app/db.py`) is a separate, deeper gap: `GET /calls/{call_id}/timeline` never selects or returns it (confirmed by reading `get_timeline` in full), so surfacing it would require a backend/API change — explicitly out of this "copy only" story's scope (AC9) and left as an open item; a future story (or `deferred-work.md` entry, added at this story's own code-review stage) should close it.

### Terminology audit result

A full audit of `frontend/src` (every `.tsx`/`.ts`/`.css` file, plus a targeted `grep` for `!`, "definitely", "certain", "Great", hype phrasing) found **no existing violation** of AC3 (Sentiment/Emotion field separation — `AnalysisDashboard.tsx`'s two summary cells, `CallRow.tsx`'s sentiment/emotion line, and `Timeline.tsx`'s `fused_sentiment`-keyed rendering all already key off the correct, distinct field), AC4 (tag/reason pairing — `_low_confidence_flag` in `web-api/app/routers/calls.py` guarantees `flag_reason` is non-null whenever `low_confidence_flag` is true, so `TranscriptPanel.tsx`'s conditional reason render is never bare in practice; the `conflict` tag's paired "reason" is the adjacent `DualSignalPanel`, confirmed against the mockup's own markup, which shows no separate reason sentence next to `CONFLICT`), AC6 (no unqualified accuracy claims anywhere — only per-Call Confidence values are ever shown), or AC7 (no hype register — zero exclamation points, no anthropomorphizing, confirmed by grep). This means Tasks 5 (AC3) is a regression-test-only task with no production code change, and AC4/AC6/AC7 need no task at all beyond this documented audit — do not "fix" what is already correct; adding unrequested code for an already-compliant AC is scope creep (Story 2.5's own "What NOT to build" precedent).

### Whole-Call speaker-attribution-unavailable note

Mirrors Story 2.5's own "Speaker-attribution data gap" finding: no `TranscriptTurn` row anywhere in this codebase has ever had a populated `speaker_label` (no DB column exists; Epic 3 is `backlog`). This story's AC5 copy contract is therefore honest-but-universal today — on every real Call, `hasNoSpeakerAttribution` will be `true`, and the note will always render, until some future Epic 3 story starts populating `speaker_label` on at least some turns. This is the same "build the contract now, it activates for real later" posture Story 2.5 took for `SpeakerLabel` itself — not a bug, not a reason to skip the AC. UX-DR7 additionally describes an equivalent note on the **Call row** (Session Call List) — that surface is explicitly out of this story's scope (epics.md's own AC427 text says "its Dashboard renders," not the Call row), and `CallRow.tsx` (confirmed, full read) has no such note today — a pre-existing Story 2.2 implementation gap, not something this story introduces or is responsible for closing. Flagged here, not silently expanded into.
