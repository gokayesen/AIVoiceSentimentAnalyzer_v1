# Story 1.10: Call Deletion (Backend)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Analyst,
I want a Call and everything it produced to be permanently and atomically removable,
so that I can keep my session's data minimal, consistent with the product's no-persistent-retention posture, and trust that "delete" means fully gone.

## Acceptance Criteria

1. **Given** a Call (in any status) is deleted, **When** the delete endpoint is invoked, **Then** the Call's SQLite rows (Call, AnalysisResult, TranscriptTurn, TimelineSegment) and its filesystem artifacts (audio, intermediates) are removed together, atomically — never one without the other (AD-12).
2. **Given** a Call with an in-flight (`queued` or `processing`) RQ job is deleted, **When** the delete request arrives, **Then** the system first cancels or awaits that job's completion before removing the Call's rows and artifacts — delete must never race a live job's writes (AD-12).
3. **And** delete is exposed as a backend endpoint only in this story (no UI) — the Delete UI (action trigger, confirm dialog, deleting state, success/error feedback) is Epic 2's Story 2.3, which calls this endpoint.
4. **And** this endpoint has independently-runnable unit tests (AD-21).

**Dependency (from epics.md):** requires Story 1.1 (Call exists to be deleted, `POST /calls`) and Story 1.2 (RQ job queue/worker lifecycle, for in-flight job cancellation). Split out of Story 1.2 to isolate deletion as its own independently testable concern, distinct from async processing/ingest — Epic 2's Story 2.3 is the UI consumer of this endpoint, not built here.

**Service placement (confirmed from Architecture's own Capability → Architecture Map, line 279):** `"§10 delete/retention | web-api delete endpoint, dual-store removal | AD-12"` — this story is entirely `web-api`-internal. It requires **zero changes to any `ml-service` pipeline file** (see "Why no `ml-service` changes are needed" below) — a mirror-image scoping fact to Story 1.9, which was 100% `ml-service`-internal.

## Dev Notes

### Why no `ml-service` changes are needed — the fan-in job chain, and why "cancel" only ever needs one, web-api-controlled job ID

This is the single most important research finding for this story, and getting it wrong either produces a broken implementation (naive job-ID lookups that silently do nothing after the first pipeline stage) or a wildly over-scoped one (threading a cancellation/abort flag through all five `ml-service` pipeline stages). Read `ml-service/app/pipeline/{ingest,acoustic,transcript}/run.py` and `ml-service/app/pipeline/transcript/sentiment_run.py`/`fusion/run.py` yourself to confirm this before implementing:

- A Call's full analysis is **not one RQ job** — it is a chain of up to five separately-enqueued jobs across five queues (`ingest` → `acoustic` → `transcript` → `text-sentiment` → `fusion`), each stage's `run_*` function enqueueing the *next* stage's job only after it finishes successfully (`acoustic/run.py` enqueues onto `get_transcript_queue()`, `transcript/run.py` enqueues onto `get_text_sentiment_queue()` or directly onto `get_fusion_queue()` via one of several fan-in fallback paths documented in `fusion/run.py`'s own module docstring, etc.). None of these downstream enqueue calls pass an explicit `job_id=` — each gets an RQ-assigned random UUID that `web-api` has no way to know in advance, and `web-api` never imports any of this `ml-service` pipeline code to find out (AD-7).
- However: `Call.status` is **not** a per-stage state machine. Grep confirms it: `ingest/run.py` is the *only* place that writes `status="processing"` (once, at the very start of the whole pipeline); `fusion/run.py` is the *only* place that writes `status="complete"`; failures write `status="failed"` from whichever stage failed. So `"processing"` covers the *entire* multi-stage pipeline, not just the ingest stage — this is exactly AD-13's own stated 4-state model (`queued → processing → complete → failed`), confirmed by reading the code, not just the architecture prose.
- Because of this, "cancel or await" (AD-12) naturally splits into two genuinely different situations, not a free choice between two techniques for the same situation:
  - **`status == "queued"`**: the *only* job that can possibly exist for this Call is the one `web-api` itself enqueued at upload time (`enqueue_ingest`) — no downstream stage has ever run, so no downstream job has ever been created. This is the one moment in the Call's entire lifecycle where `web-api` can know, with certainty, exactly which job to act on — *if* it controls that job's ID. Task 2's one-line change (`job_id=call_id`) is what makes this possible: `Job.fetch(call_id, ...)` now deterministically finds it, and `job.cancel()` removes it from the queue before the worker ever picks it up. Nothing in `ml-service` needs to change for this case.
  - **`status == "processing"`**: some stage, somewhere in the five-stage chain, is either running right now or about to be dequeued next — and `web-api` has no reliable way to know which queue or which auto-generated job ID that is without either (a) giving every one of `ml-service`'s ~8 downstream enqueue call sites the same `job_id=call_id` treatment (touching five files it does not own, `AD-7`-adjacent scope creep, and still racy — job IDs would collide/overwrite across sequential stages, workable but fragile) or (b) searching all five queues plus every worker's `get_current_job()` for matching args (real, but heavyweight, RQ introspection this story's scope does not warrant). Given AD-12 explicitly offers **await** as an equally valid alternative to cancel, and `Call.status` is already the single source of truth for "is this Call still being worked on" (AD-13), polling *that* single column to its terminal value is both correct and dramatically simpler than any form of true mid-pipeline job interruption. This is the deliberate, documented interpretation this story implements — not a corner cut.
  - **`status in ("complete", "failed")`**: no in-flight job exists at all (whether it finished successfully or not, the chain terminated) — delete proceeds immediately with no RQ interaction whatsoever.
- A previously-considered alternative — RQ's `send_stop_job_command()` (interrupts a job that is *currently executing*, moving it to `FailedJobRegistry`) — was deliberately rejected for the `"processing"` case: even if the currently-active job's ID were discoverable, injecting a stop signal into a stage mid-write is a needless correctness risk (a `conn.commit()` interrupted mid-flight is a much worse failure mode than simply waiting a bounded number of seconds for the already-in-progress, atomically-committing stage to finish on its own — every stage's persist function in `ml-service/app/db.py` already computes everything in memory and commits once, per Stories 1.3–1.6's own atomicity discipline, so waiting for "the current stage's one commit" to land is bounded and safe, whereas interrupting it is not).

### Delete ordering: DB first, then filesystem

`shutil.rmtree(...)` and the SQLite transaction are not jointly transactional — true two-phase-commit atomicity across a filesystem and a database is out of scope for this project's complexity budget. Given that constraint, the DB delete must commit *before* the filesystem removal is attempted (not the reverse), because the failure mode of "DB rows gone, files still present" is an inert orphaned directory (no functional bug — the Call is already gone from every API's perspective, `GET .../timeline` on it now 404s), while the reverse order's failure mode ("files gone, DB rows still present") is a live, visibly broken Call: any subsequent read of that Call's rows would reference audio/intermediates that no longer exist, a real correctness bug, not just wasted disk space. This mirrors `upload_call`'s own existing precedent of treating storage cleanup as best-effort (`ignore_errors=True`) secondary to the authoritative DB state.

### Reused error/response conventions

- `errors.call_not_found` (Story 1.7) is reused as-is for an unknown `call_id` on `DELETE` — no new 404 helper needed.
- The new `errors.call_deletion_in_progress` (409) follows `errors.call_not_complete`'s exact existing shape (`error_code`, `message`, `next_step`, `status_code=409`) — do not invent a different error envelope.
