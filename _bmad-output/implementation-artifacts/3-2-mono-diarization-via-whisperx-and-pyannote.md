# Story 3.2: Mono Diarization via WhisperX + pyannote

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Analyst,
I want mono Calls to be diarized into distinct speakers where possible,
so that I still get a per-speaker breakdown even when the input audio doesn't have a dedicated channel per speaker.

## Acceptance Criteria

1. **Given** a Call detected as mono (`channel_count == 1`, from Story 1.2's `detect_channel_count`), **When** speaker attribution runs, **Then** diarization is performed by WhisperX orchestrating faster-whisper transcription (Story 1.4, already persisted), forced alignment, and pyannote.audio's 4.0 Community-1 pipeline (AD-6) — no separate/duplicate transcription pass is run.
2. **Given** mono diarization, **Then** the commercial precision-2 tier, or any tier requiring a paid license, is never used (AD-6).
3. **Given** a stereo Call, **Then** this story's diarization logic never runs for it — stereo input never invokes WhisperX or diarization (AD-2, AD-6).
4. **Given** diarization produces speaker clusters, **When** speaker identity is exposed to the API/UI, **Then** each cluster maps to a canonical generic label (`"Speaker A"`/`"Speaker B"`), consistent in shape with the stereo path's labels (AD-2).
5. **Given** diarization produces speaker clusters, **When** the cluster id is used internally, **Then** it is stored as separate internal provenance metadata, never as the display-facing label itself (AD-2).
6. **Given** diarization runs, **When** it produces a per-turn speaker label, **Then** it also produces a per-turn diarization confidence value, captured and stored — never discarded (AD-6, AD-10).
7. **And** this story does not implement the whole-Call "unavailable" or per-turn "uncertain" failure/uncertainty states — that is Story 3.3's scope.

**Traceability:** FR-16; AD-6.

### Implementation-time deviation: `whisperx` package dropped, pyannote.audio called directly (confirmed with user)

At implementation time, `pip install` proved `whisperx==3.8.6` (the Architecture-pinned version) declares `torch~=2.8.0` — incompatible with this project's pinned `torch==2.13.0` (used by every other already-shipped pipeline stage). Checked every whisperx release 3.2.0→3.8.6: **no version supports `pyannote.audio>=4.0` (Community-1) while also being compatible with `torch==2.13.0`** — Community-1 support and the `torch~=2.8.0` pin were introduced in the same release (3.8.0). Older whisperx releases (e.g. 3.7.0) have a loose torch pin but cap `pyannote-audio<4.0.0` and default their `DiarizationPipeline` to `"pyannote/speaker-diarization-3.1"` — not Community-1, would silently violate AC2/AD-6.

`pyannote.audio==4.0.7` **in isolation** only requires `torch>=2.8.0`, satisfied by `torch==2.13.0` — the conflict is whisperx's own bundling, not an inherent pyannote requirement. **Resolution (user-confirmed):** drop `whisperx` as a dependency entirely; `diarize.py` calls `pyannote.audio.Pipeline.from_pretrained("pyannote/speaker-diarization-community-1", token=HF_TOKEN)` directly, and implements its own word-to-speaker time-overlap lookup (`_speaker_at`, mirroring `fusion/overlap.py`'s existing pattern) instead of WhisperX's `assign_word_speakers`. Forced re-alignment (WhisperX's `align()`) is skipped entirely — this relies on faster-whisper's own already-persisted word-level timestamps (Story 1.4) rather than a second alignment pass. This is a deviation from AD-6's literal "WhisperX orchestrating... forced alignment" wording, but preserves the exact pinned diarization model/tier (AC1/AC2 unaffected) — the alternative (downgrading `torch`/`transformers` project-wide to satisfy whisperx) was rejected as disproportionate blast radius against Stories 1.3/1.4/1.5's already-shipped, tested pipeline stages. `pyproject.toml` now pins only `pyannote.audio==4.0.7`, no `whisperx` line.

### The community-1 tier has no native per-turn confidence score — this is a real architecture gap, not an oversight

pyannote's free, open-source **Community-1** pipeline (the only tier AD-6 permits) returns discrete speaker turns (a `pyannote.core.Annotation`) with no numeric confidence attached to any turn. Per-turn **confidence scores are an explicitly named premium feature of the paid precision-2 tier** ("advanced features such as voiceprinting and confidence scores" — pyannote.audio's own docs, retrieved via Context7 2026-08-17) — the exact tier AD-6 forbids using. AD-6/AD-10 nonetheless require a per-turn confidence value to be captured and stored. This story resolves the gap the same way Story 3.1 resolved "no confidence exists for a deterministic path" (by not inventing a fake ML confidence) and the same way prior stories picked model/library specifics not fixed at the Architecture level (Story 1.3's classifier, Story 1.4's Whisper size): a **word-level speaker-agreement ratio** (Task 3, step 6) — the fraction of a turn's diarization-assigned words that agree with that turn's majority speaker. This is a dev-agent decision, not an Architecture mandate, but it is directly faithful to AD-6's own stated expectation ("diarization confidence is expected to be systematically lower during overlapping/emotionally-charged speech") — a turn whose words split across two diarization-assigned speakers (the literal signature of overlapping speech) produces a lower ratio by construction, without needing the paid tier.

### Why diarization runs once per Call, not once per VAD segment (unlike STT/SER and unlike stereo's per-turn `assign_stereo_speaker`)

AD-11 fixes VAD chunk boundaries as the single source for STT/SER model-input chunking and the Emotional Timeline — it does not require every downstream consumer to operate within one VAD segment at a time. Speaker diarization/clustering is not sound when run independently per segment: pyannote clusters speakers by voice-embedding similarity *within whatever audio it's given*, so running it separately on each VAD chunk would produce inconsistent cluster ids across chunks (chunk 2's "SPEAKER_00" is not guaranteed to be the same physical speaker as chunk 1's "SPEAKER_00"). Story 3.1's `assign_stereo_speaker` is a different, safe case for per-turn/per-segment operation because it's a stateless, deterministic per-window energy comparison — it has no cross-window clustering to keep consistent. Diarization must therefore run once across the full-Call `mono_waveform`, after all segments have already been independently transcribed (Story 1.4's existing per-segment loop is unchanged), then each already-produced turn is assigned a speaker via `assign_word_speakers`'s overlap join against that one whole-Call diarization result — this is why Task 4 restructures `run_transcript` to run diarization as a distinct post-loop pass rather than inline per-turn like Story 3.1's stereo wiring.

### `HF_TOKEN` gating — no real token exists in this dev/CI environment, and this story must not require one for tests

pyannote's Community-1 pipeline is **HF-gated**: downloading its weights requires accepting usage conditions on the model's Hugging Face page and providing a valid, authenticated access token (verified via Context7 2026-08-17, `pyannote/pyannote-audio` docs). No `HF_TOKEN` is configured anywhere in this repo today (`.github/workflows/ci.yml`, `docker-compose.yml` — checked, absent) and this story does not add one as a CI secret. **Every test added by this story must monkeypatch at the `diarize_mono_turns`/`diarize.py` module boundary and must never attempt to load a real WhisperX align model, a real `DiarizationPipeline`, or reach the network** — this is not optional test-writing style, it's the only way this story's tests can pass in this environment at all (same category of hard constraint as Story 1.3/1.4/1.5's local-only-inference tests, just enforced by an actual missing credential rather than by policy alone).

### Debug Log References

- **`whisperx==3.8.6` (Architecture-pinned) is uninstallable alongside this project's pinned `torch==2.13.0`**: `pip install` failed with `ResolutionImpossible` — `whisperx 3.8.6 depends on torch~=2.8.0`. Checked every whisperx release from 3.2.0 to 3.8.6: no version supports `pyannote.audio>=4.0` (Community-1, the AD-6-mandated tier) while also being compatible with `torch==2.13.0` — Community-1 support and the `torch~=2.8.0` pin were introduced together in the same release (3.8.0). Older releases (e.g. 3.7.0) have a loose torch pin but cap `pyannote-audio<4.0.0` and default to `"pyannote/speaker-diarization-3.1"`, not Community-1 — verified this would silently violate AC2/AD-6, not a safe substitute. Presented this to the user as a HALT (three options: use whisperx 3.7.0, downgrade torch/transformers project-wide, or drop whisperx and call pyannote.audio directly); user chose the third after the first option was verified non-viable. Resolved by dropping `whisperx` from `pyproject.toml` entirely and calling `pyannote.audio.Pipeline` directly in `diarize.py`, implementing a custom word-to-speaker time-overlap lookup (`_speaker_at`) instead of WhisperX's `assign_word_speakers`, and skipping WhisperX's forced-realignment step (relies on faster-whisper's Story 1.4 word timestamps directly). `pyannote.audio==4.0.7` alone only requires `torch>=2.8.0`, satisfied by `torch==2.13.0` — confirmed via `pip install --dry-run` before finalizing. Full rationale in the story's Dev Notes ("Implementation-time deviation" section).
- **Discovered mid-implementation**: without an `HF_TOKEN`, `diarize_mono_turns` would otherwise attempt a real network call (even just for the public-but-still-networked parts) on every pre-existing mono-audio test in `test_transcript_run.py` (`speech.wav`-based tests, none of which previously exercised any speaker-attribution code path). Added a fail-fast `HF_TOKEN` guard at the very top of `diarize_mono_turns` (before any pipeline construction) so every environment lacking a real token — this one included — degrades to a fast, local, per-Call diarization failure (caught by `run_transcript`'s existing AD-1 try/except) rather than a slow/flaky network attempt. This required no changes to any pre-existing Story-1.4 test file.
- Intermittent DNS resolution failures for `models.silero.ai` (the `speech.wav` fixture's source, Story 1.4) inside the Docker test container during this session — transient, unrelated to this story's code; resolved itself on retry. Full suite re-run confirmed clean (136/136) once network was stable.
- Verified all ml-service tests inside the `ml-service-test:cached` Docker image (Story 3.1's precedent — `torch==2.13.0` has no macOS x86_64/Intel wheel, host installs fail on this dev machine), re-running `pip install -e ".[dev]"` inside it to pick up this story's new `pyannote.audio` dependency before testing.
