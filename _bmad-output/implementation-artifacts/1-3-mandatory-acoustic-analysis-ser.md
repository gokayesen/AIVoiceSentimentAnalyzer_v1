# Story 1.3: Mandatory Acoustic Analysis (SER)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Analyst,
I want every Call analyzed for its acoustic/voice signal,
so that tone and vocal delivery are always part of the analysis — never skipped or silently replaced by text-only analysis.

## Acceptance Criteria

1. **Given** a Call has completed ingest, **when** the acoustic-analysis filter runs, **then** it runs for every `TimelineSegment` using an embedding-based model (Wav2Vec2/HuBERT/WavLM-family fine-tune), producing an Emotion output kept distinct from any text-derived Sentiment (AD-3, FR-5). [Source: epics.md#Story 1.3; AD-3]
2. **Given** the filter runs, **when** it produces its Emotion output, **then** it also computes and persists a handcrafted acoustic-feature set (pitch/F0, energy, speaking rate, pauses/voice-activity) as a mandatory `ACOUSTIC_EVIDENCE` row per segment — never optional or debug-only (AD-3). [Source: epics.md#Story 1.3; AD-3]
3. **Given** handcrafted-feature extraction, **then** it uses only librosa/torchaudio — openSMILE/eGeMAPS and Praat/parselmouth must never be used (AD-3, license constraint). [Source: epics.md#Story 1.3; AD-3]
4. **Given** an acoustic Emotion classification, **then** it maps through one fixed lookup table to exactly one of the four Sentiment polarity colors, using a small coarse category set (AD-4). [Source: epics.md#Story 1.3; AD-4]
5. **Given** the filter's native softmax confidence, **then** it is calibrated via temperature scaling before use downstream (AD-9). [Source: epics.md#Story 1.3; AD-9]
6. **Given** the acoustic filter fails, is skipped, or its calibrated confidence falls below a defined sanity floor, **when** this occurs, **then** the filter itself raises a job failure, the Call's status goes to `failed`, and there is no fallback path (AD-1). [Source: epics.md#Story 1.3; AD-1]
7. **Given** the acoustic filter's calibrated confidence, **then** the **sanity floor** (AD-1, config key `acoustic_sanity_floor`) is a distinct concept from the **low-confidence threshold** (Story 1.8, config key `low_confidence_threshold`): falling below the sanity floor means the result is invalid/degenerate and fails the Call outright — never merely flagged and shown. A result at or above the sanity floor but still below the low-confidence threshold is valid, retained, and passed downstream as a Low-Confidence Segment (Story 1.8), never discarded or failed. **And** both thresholds are documented in config with their distinct semantics and relative ordering (`acoustic_sanity_floor` lower than `low_confidence_threshold`) — never hardcoded in pipeline code, never treated as the same value. [Source: epics.md#Story 1.3; AD-1, Consistency Conventions]
8. **Given** this failure state, **then** the Call is never completed using a transcript-only or degraded-acoustic result — acoustic analysis can never be bypassed, and a transcript-only fallback is forbidden under any condition (AD-1). [Source: epics.md#Story 1.3; AD-1]
9. **Given** a Call successfully completes acoustic analysis, **when** transcript analysis has not yet run or later fails, **then** the acoustic Emotion signal still exists and is independently valid (FR-4). [Source: epics.md#Story 1.3; FR-4]
10. **Given** the acoustic classifier, **when** evaluated, **then** its accuracy is benchmarked against a majority-class baseline first, and any public-benchmark figure (IEMOCAP/CREMA-D) is labeled an optimistic upper bound pending in-domain validation (AD-17). [Source: epics.md#Story 1.3; AD-17]
11. **And** acoustic inference runs locally only — no cloud SER API call is made (AD-14). [Source: epics.md#Story 1.3; AD-14]
12. **And** the acoustic module has independently-runnable unit tests (AD-21). [Source: epics.md#Story 1.3; AD-21]

### Review Findings (AI)

- [x] [Review][Defer] `ACOUSTIC_SANITY_FLOOR` (0.15) is mathematically unreachable for the 4-class model — AD-1's core safety mechanism is dead code. — For any 4-class softmax, the maximum class probability is always ≥ 1/4 = 0.25 (uniform is the minimum-max case; temperature scaling only flattens toward uniform, never below it — `ACOUSTIC_TEMPERATURE`'s 1.0 default makes this a no-op anyway). Since `ACOUSTIC_SANITY_FLOOR` defaults to 0.15 (`app/config.py:45`) and the check in `app/pipeline/acoustic/run.py:80` is `confidence < ACOUSTIC_SANITY_FLOOR`, `AcousticSanityFloorError` can never fire against real classifier output — only against test doubles that monkeypatch `classify_segment` directly (`tests/test_acoustic_run.py`'s sanity-floor test). AC6/AC7 require this floor to be able to fail a Call on a genuinely degenerate result; right now it structurally cannot. — deferred: to be addressed as part of AD-17's real calibration/threshold-tuning work, not in isolation.
- [x] [Review][Defer] No idempotency/upsert guard for `run_acoustic`'s and `run_ingest`'s writes — retrying either job after a partial failure hits a PRIMARY KEY violation or duplicates segments. — `app/db.py`'s `insert_acoustic_evidence` (called from `app/pipeline/acoustic/run.py:89`) does a plain `INSERT` keyed on `segment_id` (PK); if a worker crash lands between its commit and `set_segment_acoustic_results`'s commit (see the atomicity patch item below) and the job is ever re-run for the same Call, the second `INSERT` violates the PK and permanently fails the Call on every subsequent attempt. ### Architecture compliance (non-negotiable)

- **AD-1 (voice-first, no bypass):** the acoustic filter must run to completion for every Call; any failure (including a sanity-floor breach) fails the whole Call via `Call.status = "failed"` — never a partial/degraded/transcript-only result. Since the transcript pipeline doesn't exist yet in this codebase, there is no fallback code path to accidentally build here — keep it that way.
- **AD-3 (embedding model + mandatory handcrafted layer, both required, kept distinct):** the classifier's Emotion+confidence output (`TimelineSegment.acoustic_emotion`/`acoustic_confidence`) and the handcrafted-feature explainability layer (`ACOUSTIC_EVIDENCE`, one row per segment) are two separate, both-mandatory outputs — never conditional, never merged into one blob.
- **AD-4 (coarse taxonomy → fixed polarity lookup):** the classifier's raw 8-class output is first collapsed to a 6-class canonical Emotion taxonomy (satisfying AD-4's explicit "4-6 classes" bound), then every canonical Emotion maps through exactly one fixed table to one of `negative`/`mixed`/`positive`/`neutral` (verified UX token names). ### Latest tech information (verified via Context7, 2026-08-12)

- **`transformers` audio classification pattern** (`/huggingface/transformers`): `AutoModelForAudioClassification.from_pretrained(model_name)` + feature extractor preprocessing, then `with torch.no_grad(): logits = model(**inputs).logits` — raw logits, apply temperature scaling and softmax yourself for calibrated confidence (AC 5); do not use the high-level `pipeline("audio-classification", ...)` helper for the actual inference path, since it returns only its own uncalibrated softmax score, not raw logits.
- **`librosa.pyin`** (`/librosa/librosa`): returns `(f0, voiced_flag, voiced_prob)` — `voiced_flag` is a per-frame boolean array; unvoiced frames in `f0` are filled with `fill_na` (default `NaN`) unless overridden. Use `voiced_flag` both for `pitch_mean_hz`/`pitch_std_hz` (mask to voiced frames only) and to derive `pause_ratio`.
- **`ehcalabres/wav2vec2-lg-xlsr-en-speech-emotion-recognition`** (verified via web search of its Hugging Face model card/commit history): apache-2.0 license, genuinely fine-tuned `Wav2Vec2ForSequenceClassification` (re-trained on RAVDESS, per the model's own commit history — not a frozen-backbone probe), 8 labels (`angry`/`calm`/`disgust`/`fearful`/`happy`/`neutral`/`sad`/`surprised`), 82.23% eval accuracy on RAVDESS — verify exact `id2label` string spellings from the model's own `config.json` at implementation time rather than assuming.
