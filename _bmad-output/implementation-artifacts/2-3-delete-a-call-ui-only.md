# Story 2.3: Delete a Call (UI only)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Analyst,
I want to delete a Call I no longer need from either the Call row or its Dashboard,
so that I can keep my session's list relevant without carrying data I don't need.

## Acceptance Criteria

1. **Given** a Call row, **When** the Analyst hovers or focuses it, **Then** a delete `icon-button` is revealed (transparent by default, destructive-hover red foreground) — hidden otherwise.
2. **Given** the Analyst is viewing a Call's Dashboard, **When** they choose to delete it, **Then** the same delete action is available there, using the identical `confirm-dialog` component as the Call row's. **See Dev Notes "Known spec gap — no Dashboard exists yet" before starting**: the Analysis Dashboard is Story 2.4 (still `backlog`), so this half of the AC cannot be wired into a real Dashboard surface in this story. Build `ConfirmDialog` as a standalone, presentation-agnostic component Story 2.4 can drop in unmodified; only actually wire the Call-row half of this AC now.
3. **Given** delete is triggered (either surface), **When** the confirm dialog opens, **Then** it states the Call's filename and that deletion is immediate and unrecoverable, with Cancel (default focus, no change) and Delete (destructive-styled, confirms).
4. **Given** the dialog is open, **When** the Analyst presses Escape or clicks the overlay, **Then** it behaves identically to Cancel.
5. **Given** the Analyst confirms Delete, **When** the request is sent, **Then** it calls Story 1.10's backend delete endpoint — no delete/atomic-store logic is implemented in this story.
6. **Given** the delete request is in flight, **When** the UI reflects it, **Then** the row (or Dashboard) shows a "deleting" state. (The Dashboard half is the same known gap as AC2 — row-only in this story.)
7. **Given** the delete succeeds, **When** the response returns, **Then** the Call is removed from the list immediately (no undo); if it was open in the Dashboard, the Analyst returns to the Session Call List. (The Dashboard-return clause is the same known gap as AC2 — not applicable, no Dashboard/routing exists to return from.)
8. **Given** the delete request fails, **When** the response returns, **Then** the UI shows a clear error and the Call remains in the list, undeleted.
9. **Given** the Analyst cancels or dismisses the dialog, **Then** nothing changes.

**Traceability:** UX-DR9; consumes AD-12 (Story 1.10) — not re-implemented here.

**Dependency:** Story 2.1 (App shell, `SessionCallList`/`CallRow` structure, DESIGN.md token system). Story 2.2 (`CallRow`'s five-state render logic, `callsApi.ts`'s `ApiError`/base-URL pattern, `CORSMiddleware` already configured with `DELETE` in `allow_methods` — verified in `web-api/app/main.py`, no backend change needed this story). Story 1.10 (`DELETE /calls/{call_id}` — fully implemented, tested, atomic dual-store removal with in-flight-job cancel/await per AD-12; this story is purely its UI consumer).

## Dev Notes

### Known spec gap — no Dashboard exists yet (read before starting Task 3/4)

AC2, part of AC6, and part of AC7 all reference "the Dashboard" as a second surface delete can be triggered from and returned to. The Analysis Dashboard is Story 2.4's deliverable (`_bmad-output/implementation-artifacts/sprint-status.yaml`: `2-4-...` is still `backlog`) — it does not exist in this codebase yet, and `mockups/analysis-dashboard.html` (checked directly) has **no** delete affordance in it at all, confirming there is nothing to visually transcribe even if a Dashboard page existed. This mirrors the exact shape of Story 2.2's AC9 gap (a spec line assumes something Epic 1/Epic 2's own sequencing hasn't built yet) and the same resolution approach applies: **build the reusable piece now, wire only what exists now.** `ConfirmDialog` (Task 3) is deliberately built as a standalone, props-only component with zero dependency on where it's rendered from — Story 2.4 can import and mount it from the Dashboard unmodified when that story is built. Do not build a Dashboard placeholder page, a route, or any routing library to "complete" AC2/AC7 — that is exactly the scope creep Story 2.2's own Dev Notes ("What NOT to build") already ruled out for this exact reason ("No delete UI/`confirm-dialog`, no delete `icon-button` on the row — Story 2.3" was *this* story's own forward-reference; the mirror-image forward-reference to Story 2.4 applies the same way now).

### Delete is available on every row state, not just `complete`

AC1's "a Call row" is unqualified — and the backend's `DELETE /calls/{call_id}` (Story 1.10, `web-api/app/routers/calls.py:366-433`) explicitly handles deleting a `queued` Call (cancels its RQ job) and a `processing` Call (awaits completion, bounded by `DELETE_AWAIT_TIMEOUT_SECONDS`, before deleting) — this was built specifically so delete works regardless of a Call's lifecycle stage. Do not restrict the delete `icon-button` to only the `complete`-state branch of `CallRow`; it must appear (hover/focus-revealed) on all five states, including `validating` (client-side only, no backend Call exists yet for a `validating` row — deleting one is really just a local-state removal with no `deleteCall` call needed at all, since there's no `call_id` yet to delete; a `validating` row's delete affordance can simply remove it from local state directly, bypassing the confirm-dialog+API round trip entirely, since nothing has been persisted server-side to warn about — this is a reasonable implementation simplification, not a literal AC requirement, since the epics don't distinguish this edge case).

### Delete error fields are new, not a reuse of `errorMessage`/`errorNextStep`

Story 2.2 established `SessionCall.errorMessage`/`errorNextStep` as fields with one specific meaning: they drive the `failed`-state row's entire card layout (filename + message + next-step + Retry button, `.call-row--failed` background). A delete failure is a different event that can happen to a row in *any* `state`, including `complete` — forcing a `complete` row into the `failed` visual treatment because its *delete* failed (not its upload/processing) would be misleading (the Call itself is fine; only the delete attempt failed) and would destroy the Sentiment/Emotion/confidence/duration data still worth showing. Hence `deleteError`/`deleteErrorNextStep` as separate, orthogonal fields (Task 2), rendered as a small addition to whatever the row already shows (Task 5), not a replacement of it.

### No backend changes in this story — verified, not assumed

Read `web-api/app/routers/calls.py` end-to-end (Story 1.10's `delete_call_endpoint`) and `web-api/app/main.py` (Story 2.2's `CORSMiddleware`) in full: the delete endpoint is complete, atomic, tested (67/67 passing suite includes `web-api/tests/test_delete.py`'s 7 tests covering AC1/AC2 exhaustively), and `CORSMiddleware`'s `allow_methods` already includes `"DELETE"` (added in Story 2.2, verified present) — a cross-origin `DELETE` request from the frontend will not hit a CORS block. This story touches zero backend files. If Task 8's manual verification somehow surfaces a CORS or 405 issue, that is a signal something regressed from Story 2.2, not a gap this story needs to newly close.

### Confirm-dialog copy is verbatim from the mockup, not the epics' paraphrase

`epics.md`'s AC3 paraphrases the dialog copy ("states that deletion is immediate and unrecoverable"); the actual wording to render is `mockups/confirm-dialog.html`'s literal text (the only visual reference for this component, verified by direct read): title `Delete {filename}?`, body `This removes the Call and its Analysis Result from this session.`, warning `This action is immediate and unrecoverable — nothing is retained beyond the current session.` Use this text exactly — it is also the PRD §10 / AD-12 canonical phrasing ("immediate and unrecoverable"), not this story's own invention.
